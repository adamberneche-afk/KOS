# CAS — Classroom Agency System

A district-deployed (`ccpsnet.net` / CCPS), FERPA-scoped, student-facing
Google Apps Script platform for a Sports/Entertainment/Event Marketing
course pair (course codes **8175** and **8177**). Built on the same
no-external-API-keys, Gemini-native pattern used elsewhere in this repo's
`kos-personal/` system, but otherwise an unrelated codebase.

The curriculum's pedagogical spine is a simulated student-run
**"conglomerate"** business spanning 10 stages (Foundation → Industry/Producer
→ Product → Market Conditions → Price → Rules of the Chain →
Place/Distribution → Promotion → Strategy/Synthesis → Consumer→Producer),
with named divisions (Creative Studio, Apparel & Merch Co., School Store,
Wholesale & Sourcing, Media & PR, Events Division, Esports Division) and
management roles students rotate through. See `curriculum/lesson-cards/`.

## Student data access policy

Set by the operator on 2026-09-28:

1. Student data is visible only to the student and their teachers, and only
   during the current school year.
2. Only the student can edit, and only before submission.
3. Only the teacher who assigned the work can grade it and give feedback.

How the code enforces it:

| Where | What it does |
|---|---|
| Intake (`02`) | The assigning teacher is the owner of the matrix the assignment came from (MatrixRegistry), not the form's student-typed "Teacher Email". The doc is shared with its student (edit) and that teacher (comment) only. It no longer goes into a class folder every classmate could view. |
| Submission (`04`, `25`) | With `WARMUP_TEXT_BOX` on, a warm-up has no doc: it is answered on the Student Dashboard on its lesson day; a missed one can be answered late until the end of the student's next class day, scored without feedback or extra credit (2026-10-24). A warm-up doc locks when its extra-credit window closes: the student can read it, not edit it (`_lockDocAfterSubmission_()`, kept in `04` as a shared helper). Assignment docs are never locked: turn-in is on Canvas, and the Turn-In Form that used to lock a passing doc was retired (handler 2026-10-10, forms 2026-10-12). |
| School year (`00`) | `_currentSchoolYear_()` is `CURRENT_TERM`'s school year, else the year today falls in (starting in August). `CURRENT_TERM` is the school year plus the marking period, `2627_MP1` (MP 1-4; older terms like "2025-26 S1" still read). Since 2026-10-19 the marking period rolls over by date (`currentTerm_()`): `MARKING_PERIOD_ENDS` (`2627_MP1=2026-10-30,...`, a Script Property or a Ledger `_CONFIG` row; the 2026-27 calendar is built in) picks the period within `CURRENT_TERM`'s school year, and `CURRENT_TERM` is used as set on a date the table doesn't cover. Enrollment checks (warm-ups, roster, artifact sync, Canvas import) compare the school year, not the marking period. The marking period only labels new rows: the dashboards show the whole year by default, and archiving takes a whole school year. The Teacher Dashboard, the roster, the student dashboard and parent reports show the current year only, whatever term the page asks for. |
| Grading (`07`, `10`) | Turn-in scores need the row's `TEACHER_EMAIL`. SCR ratings are shown to, and decided by, the teacher whose assignment produced the evidence (CompetencyEvidence's `config_id`). The Teacher Dashboard is the only SCR writer (the central-ledger copies in `30` and `30b`, never called, were deleted 2026-11-07). `manuallyMarkCompliant` checks the signed-in user. |
| Parent reports (`36`) | Scoped to the dashboard's own teacher, this year, and only that teacher's courses and decisions. |
| Shared web apps (`00b`, since 2026-10-31) | Both dashboards run as the teacher with domain access, so a student who opens one can call any public function of its project from the page, and it runs as the teacher. Every public function there checks its caller: `_isAuthorizedTeacher_()` for the dashboard's own, `requireScriptOwner_()` (`00b_ScriptOwnerGuard.js`: the script's own account or a trigger) for setup, editor and shared functions, or it acts only on the caller's own identity and is listed in `tools/gas-lint/webapp-public-allow.json`. gas-lint fails any other (KOS Audit Docket IV: a student could overwrite a classmate's parent-report record). |
| SCR export (`30`) | Private, shared only with named central-office staff; student accounts are refused. |
| Teacher Dashboard: evaluation states (`07`, `37`) | Each Flow 2 evaluation's result goes on the student's Ledger row (`37`'s `recordEvaluationResult_()`: CheckCount, LastResult, FirstPassedAt, LastSuggestedScore, columns 24-27). The dashboard opens on the current lesson (the latest LessonSchedule start_date on or before today, per course; students are matched to lessons through StudentAssignments) and shows four states, as summary cards that filter the list and as a badge per student: ⚪ not checked yet, ✏️ checked but not passing yet, ✅ passed, ↩️ passed before with the latest check needing revision. Each row has its check count, first-pass date and the latest suggested score. In each lesson section, rows that couldn't be checked or wait on the teacher's review come first, then the rest by period and name. |
| Student dashboard | Runs as the deploying admin with domain access, so students need no access to the Central Ledger. Its **Submit for Feedback** button (`submitMyWork()`) is how students submit: the district turns Apps Script off for student accounts, so the doc menu (`01`) never appears for them (found 2026-10-08). The button checks the signed-in student owns the Ledger row, reads the doc as the admin to apply the menu's minimums (150 characters, 25 words below the response line), and queues the same `ReviewQueue` row. It refuses a second submit while the first is still in line (`PENDING` or `STAGED`), and it refuses a response containing text that belongs to a feedback block or the evaluator's prompt (`[SYSTEM:`, `[SUGGESTED_SCORE`, `[MILESTONE_OUTCOMES`, a submission delimiter; `findSystemText_()` in `00`, since 2026-10-10) and names the text to delete. Since 2026-10-31 (KOS Audit Docket IV) the same check refuses a warm-up answer or reply that carries system text, `[ALSO_SHOWN` is on its list, and a student's words that reach a model prompt after that check (the warm-up answer for Flow 4, the prior answer for Flow 3's lead-in, an earlier part re-read from a doc the student can still edit) go through `neutralizeSystemText_()` (`00`), which replaces each token with "(system text removed)". Flow 2's `ALSO_SHOWN` line is read from the last one in the output, the evaluator's own. The writing is counted, never returned or stored. Reading the doc is why the manifest has the `documents` scope. |
| Student dashboard: cards (`13`, since 2026-11-07) | Each card has a short pill (`statusPill`: Not started, Waiting for feedback, Being checked, Revise, Passed ✓, Turned in, Done ✓, Taking longer ⚠, Couldn’t be checked ⚠) and the rest of the status on its own line (`statusNote`); `displayStatus` is unchanged for the doc menu. One filled button per card, by status (`primaryActionFor()`: Submit for Feedback on a card to revise, View feedback on a passed one, Open My Document otherwise). No "Last checked" line while the work is being checked, before it is started, or on a check that failed or timed out (its own line says what happened). A **Do next** list above the classes links to every card that needs the student (to revise, or a check that failed other than a timeout). A card to revise says **Not yet:** and the first milestone its last check didn't find, read from `CompetencyEvidence` (`_dashNotYet_()`, only when a card needs it; no new column). On a touch screen every button and menu is at least 44px tall; the Teacher Dashboard's header gets the same rule, and its student-name links a 24px target. |
| Student dashboard: demo mode (`13`, `13b`, `07`, since 2026-11-07) | A teacher sees the page as a made-up student, "Demo Student" (ID 0000000), on their real lessons: **👁 View as a student** (the Teacher Dashboard's header, under **More ▾**) opens the Student Dashboard's URL (`STUDENT_DASHBOARD_URL`) with `?demo=1`, which can be bookmarked. Who: the account the web app runs as (`requireScriptOwner_()`) or the `TEACHER_EMAIL` Script Property set on the Student Dashboard project itself; anyone else asking for `?demo=1` gets their own page, and `getDemoDashboardData()` refuses them. The page says "Demo: a made-up student. Nothing here is saved.", shows "demo" for the address, and makes one server call, `getDemoDashboardData()`, which opens no sheet, doc or file and returns the whole fixture: both courses' first five lessons (`13b`, built by `tools/cas-ccps/build-dashboard-demo-lessons.js` from `55b` and `data/CompetencyRegistry.csv`; `--check` and a test catch drift) in every card state (not started, being checked, revise with its Not yet line, couldn't be checked, passed, turned in), warm-ups, competencies and My Context, built with the same status and warm-up functions as real rows. Every other call the page makes goes through `scriptRun()` to stubs in the page (`DEMO_STUBS`); a call with no stub fails in the page. Submit for Feedback asks the real reflection question, then moves the card to Being checked and then Revise; Open My Document shows a note. Nothing is written anywhere. |
| Student doc menu (`01`, `13`) | The doc's **📊 Feedback** menu ("Submit for Feedback", "Where is my work?", "Open my dashboard"; renamed from "Run Assignment Check" / "Check My Status" on 2026-10-22): its items run as the student, so they no longer open the Ledger or the Admin sheet. They POST to the student dashboard web app (`13`'s `doPost()`), which identifies the signed-in student itself and answers only for that student's own Ledger row. `02` stamps the web app's URL into each new doc (`[SYS_DASHBOARD_URL:…]`). The doc's manifest adds `drive.readonly`, which Google requires on the token for calling a web app. |
| Student writing (`01`, `13`, `50`) | Stays in the student's own Doc. A submit (the dashboard's button, or the doc menu's "Submit for Feedback") sends only that there is writing to evaluate; `ReviewQueue`'s `StudentText` column stays empty (it used to get a full copy that nothing read), and the bridge (`03`) empties it each run in case an older doc's menu wrote it directly. `previewReviewQueueTextScrub()` then `applyReviewQueueTextScrub()` empty it in older rows; the health check flags any row still holding text. |
| Existing files, year end (`50`) | `previewStudentDataAccessRepair()` then `applyStudentDataAccessRepair()`: fixes this year's docs, revokes earlier years' (the files stay as records), removes class-folder sharing, makes exports private, and reports any student access to the Ledger. Run it again after `CURRENT_TERM` moves to a new school year. |

By the operator's choice: AI feedback and warm-up scoring stay automatic,
and the Student Context doc (`29`), which spans every teacher and year, may
stay shared with the student and their teachers.

Known gap: each student doc carries its own copy of the menu script, made
when the doc was created, and a push only changes the master template. Docs
created before the `01` change still read the Ledger and write the
ReviewQueue as the student (with their text, which the bridge then
empties), so their menu keeps needing student access to
the Central Ledger spreadsheet until those docs age out at year end.

## Family Mail Sentinel (scripts 60-62)

Student and parent mail is the most urgent mail the teacher gets and the one
kind Claude must not read. `60_FamilyMailSentinel.js` labels it `KOS/Family`
(the KOS Claude Project's mail search excludes that label), has a Gemini flow
triage it with names redacted, and writes `KOS_FAMILY_SIGNAL`: one line per
thread waiting on the teacher, with course, period, category, a one-line ask
and hours waiting, and no names. A safety message is flagged before Gemini
runs, is never summarized, and pushes to the teacher's phone (ntfy, no
details). Setup and the data boundary:
[`docs/FAMILY_MAIL_SENTINEL.md`](./docs/FAMILY_MAIL_SENTINEL.md).

## CAS attention signal (script 34b)

The KOS Claude Project may not read CAS sheets (SMP-018), so
`34b_CasAttentionSignal.js` gives it counts instead. At the end of every
queue-watchdog run (every 10 minutes) it rewrites `KOS_CAS_SIGNAL`:
students and families first (submissions waiting on feedback or failed, SCR
suggestions awaiting the teacher's confirm, students newly retry-eligible,
students rated below satisfactory on the SCR, a 4 or 5, with the change
since yesterday), then admin
(Ledger cycle jobs failing now or today, by function name, `64`; watchdog
dry run or failure, timed-out and unknown-status queue rows, rows in flight
with no timestamp, Submit for Feedback failures on the system side, the
nightly rollout's problems that remain after the day's runs, an unfinished
day and a stale Canvas export once, when LAST NIGHT doesn't already say them,
and courses still in shadow, failing FERPA checks). A line shows only above
zero; a count that can't be read says "unavailable". No names, IDs, grades or
student text. The first run creates the doc and stores its ID in
`CAS_SIGNAL_DOC_ID` (optional `CAS_SIGNAL_FOLDER_ID` picks its folder); paste
its link into the Project's instructions. Data boundary:
`docs/FERPA_DATA_MAP.md`, "CAS attention signal".

**Last night (script 34c).** The doc opens with a LAST NIGHT section from
`34c_OvernightHealth.js`: Ledger cycle jobs still failing, each 3 a.m. stage's run stamp (23, 33, 25, 24; a
quiet night stamps too, and a run ending in `ERRORS_n` or `NO_TAGS` is
reported), today's and tomorrow's warm-ups (delivered, not yet delivered,
ERROR), earlier warm-ups stuck at PENDING_EVAL, Studio jobs with no return
(Flow 2 after 15 minutes, Flows 3–5 after 30), failed warm-up returns in
the last day, and warm-ups delivered as the teacher's anchor. At most every
6 hours it also runs the setup checks that used to be editor-only (since
2026-10-23): the Ledger's column order (`38`), the FlowPrompts tab against
the code (`40`), the last day's Studio returns in the right columns (`41`)
and each retention record's date column (`57`); each problem is one line
naming the function to run. With nothing wrong it prints one all-clear line. The same
lines are emailed to `ADMIN_NOTIFY_EMAIL` (or `TEACHER_EMAIL`) once a day on
the first watchdog run after 5 a.m., with the deployment's version marker
and teacher account in the body; `CAS_OVERNIGHT_MAILED` holds the last date
sent. Counts only.

Each of the 9 projects has a real, committed `appsscript.json` and is
pushed with clasp — see [Version control (clasp)](#version-control-clasp)
below.

**Pipeline in one paragraph:** A student's doc is created from the Master
Student Template (Script 02) with four zones and invisible system-ID
stamps. The student clicks **Submit for Feedback** on their dashboard
(Script 13; Script 01's doc menu, **📊 Feedback → Submit for Feedback**,
does the same where student accounts may run Apps Script), which appends a
row to `ReviewQueue`. The Ledger's frequent jobs run from one every-minute
trigger, `runLedgerCycle` (`64`), each at its own cadence. Script 03's
`bridgeQueue` (every minute) moves `PENDING` rows to `STAGING_PIPELINE`,
deduplicating against in-flight evaluations. Script 06's turnstile (every
minute) releases one `PENDING_INFERENCE` row **per teacher lane** to
`IN_PROCESS` — a per-teacher-lane design, not the single global lane used
elsewhere in this codebase — and times out rows stuck `IN_PROCESS` for
&gt;12 minutes. Script 37 resolves the teacher's milestones (seeded from the
repo by `53`, or set up via Script 05 → Flow 1 → Script 08's confirmation
step) into one `FlowInput` row; Studio's Flow 2 reads the doc and makes the
Gemini call; 37's harvest (every 5 minutes) checks the output, writes the
feedback (a comment on the doc with `FEEDBACK_AS_COMMENT` on, otherwise the
doc's feedback zone), records the result on the Ledger row and in
`EvaluationLog`, and flips the staging row to `COMPLETE`, or to
`ERROR_EVALUATION` when the result can't be used. Script 03's
`backPropagateCompletions` (every 2 minutes) closes out the queue/ledger
rows, appends the "what to do next" block, and for a timeout or an
`ERROR_EVALUATION` emails the teacher and sets the doc header.
With `REFLECTION_ON_SUBMIT` on (off by default; `all` or one course code),
Submit first asks one or two questions about how the student worked
(fixed frames chosen in `00`, at least 10 words each), writes the answers
to the `ReflectionLog` tab and only then queues the work; 37 puts that
submission's answers into Flow 2's `PromptText` and posts them back to the
student as a comment on the doc
(`meta/STUDENT_WORK_PLAN_2026-10.md`, Phase 1).
Students turn in on Canvas, where the teacher grades. The Turn-In Form and

## Version control (clasp)

Connected: all 9 projects are live on the `ccpsnet.net` account, and the
operator pushes `main` to them with `node tools/clasp-sync/run.js --latest`
(which also moves each web app's listed deployments to the new version).
See [`meta/CLASP_AND_APPS_SCRIPT.md`](../meta/CLASP_AND_APPS_SCRIPT.md) for
the full rationale. The short version: `cas-ccps/scripts/` doesn't fit
clasp's one-folder-one-project model, since it's 8 of the 9 projects above
sharing overlapping files (`00_SharedConfig.js` alone is pasted into 8 of
them) — `studio-steps`, the 9th, lives in its own `cas-ccps/studio-steps/`
(blocked on this account; the flows were ported to `37_FlowInputBuilder.js`
and `41_WarmUpFlowBridge.js`)
folder and shares no files with the other 8.
[`tools/clasp-sync/`](../tools/clasp-sync/README.md) reconciles the
8-projects-in-one-folder problem — a script reads
`tools/gas-lint/project-map.json` and generates a throwaway per-project
push folder for each (`studio-steps` included) under
`cas-ccps/.clasp-build/` (gitignored, regenerated on demand), so
`cas-ccps/scripts/` itself never has to be reorganized or duplicated in
git. `cas-ccps/clasp/manifests/` holds each project's real
`appsscript.json`, and `cas-ccps/clasp/templates/` holds `.clasp.json`
placeholders; the deploying machine keeps the real script IDs in the
gitignored `cas-ccps/clasp/local/` (or `clasp-registry`, for `run.js`). For
`rubric-response-sheet`/`teacher-matrix-sheet` (cloned per teacher),
target the *master template* — there's no single live script ID once
teachers have their own copies.

## Where settings come from

`getConfig_()` (`00_SharedConfig.js`) checks three places in order:
1. The project's own Script Properties.
2. For the Central Ledger ID only, the spreadsheet the project is attached to.
3. The Central Ledger's `_CONFIG` tab, for district-wide values: the admin
   folder and email, the Student Dashboard URL, the email domain, the
   leader-hub OAuth client ID, the master template IDs, and the switches
   and calendar every project shares: `PIVOT_ARCHETYPE_LOCK`,
   `MARKING_PERIOD_ENDS`, `FEEDBACK_AS_COMMENT`, `WARMUP_TEXT_BOX`,
   `ROLLOUT_AUTO_APPLY`, `REFLECTION_ON_SUBMIT`, `TURN_IN_CODE_COURSES` and
   `STUDIO_DAILY_RUN_LIMIT` (`SHARED_CONFIG_KEYS` in `00`).

A project that is attached to the Ledger, or to a teacher's cloned sheet,
therefore needs no properties for these at all. The dashboards need only
`CENTRAL_LEDGER_SS_ID`. Per-teacher values and secrets are never read from
the shared tab. `seedLedgerConfigTab()` builds the tab from existing
properties; `showConfigSources()` shows where each value came from. See
[`DEPLOYMENT_HANDOFF.md`](./DEPLOYMENT_HANDOFF.md#script-properties-reference)
for which properties are safe to delete afterwards.

**The school, from configuration (packaging step 1, 2026-11-01).** What used
to be written into the code is now read through `schoolProfile_()` (`00`,
"THE SCHOOL"). Each value is a shared key, so it can be set as a Script
Property or in the Ledger's `_CONFIG` tab, and today's school is the default
when a value is unset:
- `SCHOOL_COURSES` (`8175=marketing,8177=management`): the courses and a word
  that names each. It drives `schoolCourseOf_()`, the one course-from-name
  rule that 00, 24 and 51 share, and every "for each course" loop (53, 55, 65).
- `STUDENT_EMAIL_DOMAIN` (`ccpsnet.net`) and `STUDENT_ID_PATTERN` (`\d{7}`):
  what a student account looks like (29's `_studentIdPattern_()`,
  `studentIdRegex_()`).
- `STUDENT_MAIL_DOMAIN` and `STAFF_MAIL_DOMAIN`: the Family Mail Sentinel's
  student and staff mail.
- `EARLY_RELEASE_DAYS`, `SCHOOL_DAYS_OFF` and `BELL_SCHEDULE` (JSON: class
  minutes per schedule, labels, and a rotation by weekday): the calendar.
  They feed `bellScheduleFor_()`, the lesson doc and agenda deck, the
  ⚙ Settings day choices, and `isSchoolDay_()`, which the held-part count
  (68) uses. The days off are the Ledger's `NoSchoolDays` tab (the
  district calendar; add a snow day there) plus any extra in
  `SCHOOL_DAYS_OFF`, read the first time a day is checked. A date typed
  into `_CONFIG` is read as the `yyyy-MM-dd` it was typed as.

A value that doesn't parse falls back to its default and logs `[SCHOOL]`.
Some things stay course-specific on purpose:
- the lesson and unit data (53b, 55b);
- the pacing guide's `objective_8175` / `_8177` columns (31, 23, 28);
- 51's expected registry counts.

The Unified Manual's library ID is in the manifests and comes with the
install registry (step 3). `tests/cas-ccps/school-profile.test.js` pins the
defaults and checks each override.

## Nightly lesson rollout (script 58)

`58_LessonRollout.js` (Central Ledger) ties student docs to the
`LessonSchedule` dates, so a typed start date is enough. Each night at about
9 p.m. (`installLessonRolloutTrigger()`), per course:

1. **Release.** Docs made ahead for the current lesson or one starting
   tomorrow (Ledger status `SCHEDULED`) are shared with their students and
   set `ACTIVE`, so the card appears on the Student Dashboard the night
   before the lesson.
2. **Seed.** Lessons starting within 2 days, and the current one, go into the
   TeacherMatrix as LIVE (`seedAssignments_`, script 53).
3. **Enroll.** Each of those lessons is enrolled from the Canvas exports
   (`enrollCanvasRoster_`, script 52). A lesson whose release night hasn't
   come gets unshared `SCHEDULED` docs; the current lesson and tomorrow's
   get shared ones, so late joiners can start at once.
4. **Lesson doc.** Each of those lessons gets the teacher's lesson doc once
   (script 66, below); later nights refresh its Class status.
5. **Agenda.** The next school day's agenda deck for the course (script 67,
   below).

It runs in **shadow** until `ROLLOUT_AUTO_APPLY` is set (Script Property or
the Ledger's `_CONFIG` tab: `8175`, `8177` or `all`; `off` stops it again):
in shadow it only writes what it would do. Every run writes counts and
reason codes to the `RolloutLog` tab, never student details, all stamped
with the run's start time, with a `PROBLEM` row for anything that needs you
(failed enrollments or shares, a missing template, unmapped Canvas sections,
a Canvas export more than 7 days old, checked by the nightly run only). A
step the time budget stopped is a `CONTINUES` row, its Count what is left;
it is not a problem, because the next run picks it up.

**What the signal counts (2026-11-08, plan L3).** It used to count every
PROBLEM row of the last day, so a night of catch-ups read as "57 problems".
Now `rolloutDayStatus_` (58) counts what remains: rows are grouped into runs
and keyed by course, lesson and step; a problem counts only if it is in the
latest run that touched its step (a later run that did the step clears it;
the same problem in every run counts once; a run-wide failure counts only if
the day's latest run repeated it). A `CONTINUES` row still standing after the
day's runs means the day didn't finish, with its docs left; a dry run's never
does. The stale-export note is said once. Rows logged before `CONTINUES`
("...the next run continues", "...not reached") are read as continuations.
The lines read: `Lesson rollout: 4 problems need you (see the RolloutLog
tab)`, `Lesson rollout didn't finish: 12 docs left; the next run continues`,
`Lesson rollout: the newest Canvas export is 9 days old; export a fresh
one`, and, in the overnight all-clear, `Lesson rollout: finished (3 runs)`.
The CAS signal also says while a course is still in shadow. `previewLessonRollout()` runs it once as
a dry run from the editor. The steps below still work by hand.

**Catching up (2026-10-29).** A run makes about 20 student docs before its
time budget. A run that stops short schedules `runLessonRolloutCatchUp` a
few minutes later, which does the same, until a run finishes (at most
`ROLLOUT_CATCHUP_MAX`, 12, a day). Enrollment goes to tonight's releases
first with the courses taking turns, each lesson getting an equal share of
the time left, and keeps a minute for the lesson docs and agendas. Running
`runLessonRollout()` from the editor starts the same chain. The overnight
email carries the same rollout lines as the signal.

**Hold a lesson.** `LessonSchedule`'s `release` column (2026-10-28): `HOLD`
keeps the rollout from seeding, enrolling or releasing that lesson, current
or upcoming, whatever its date; blank (or `AUTO`) is normal. The lesson is
still the one taught on its dates, and still gets its lesson doc and
agenda. Each run logs a `HOLD` row for it. The 📅 Lessons panel's
**Hold**/**Release** button sets it (`setLessonHold`, script 07);
`seedLessonSchedule()` adds the header to an older tab. Docs already shared
stay shared.
