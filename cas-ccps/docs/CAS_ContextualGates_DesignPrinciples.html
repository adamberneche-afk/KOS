The principle

Fail loudly.
At the right moment.

Most setup wizards treat completion as a binary: the script ran without errors, therefore setup is done. This is wrong. A script can run without errors and leave a system in a state that doesn't work — and the user won't find out until they're in front of a class and the "New Lesson" button doesn't appear.

A "complete" state means verified complete — not "the script ran without errors."

Contextual gates is the design practice that enforces this. Every action that has a dependency, a manual follow-up, or a correctness risk stops the user at the exact moment it matters — verifies the result, surfaces any gap, and gives a path forward. Nothing is deferred to a summary document. Nothing fails silently. The user always knows exactly what state the system is in.

The wizard should leave the teacher in a known, verified, unambiguous state at every step — and when it can't, it should make the gap visible at the point where it matters, not in a document they'll never read.

❌ The old pattern

Deferred failure

Setup runs. Summary doc is appended. Teacher clicks through the wizard, sees "Setup Complete," and closes the document. Three days later they open the Teacher Dashboard. No "New Lesson" button. They don't know why. They don't know what to fix. They email the admin.

vs
✓ The contextual gate

Verified completion

After Phase A completes, the alert shows exact redeploy steps — model, step count, what to click — before the teacher closes the wizard. The completion state is: dashboard redeployed, competency tabs verified, backfill trigger confirmed. The teacher leaves knowing exactly what they have.

The practice

Five gates.
One principle.

Every step in a setup wizard should pass through all five gates before declaring success. Gates are not optional — they are the completion condition, not a defensive afterthought.

01

Verify your own output

After every creation or write operation, read it back and confirm it landed correctly. Don't assume success because no exception was thrown. A tab creation call can succeed without the tab appearing if the spreadsheet has quota issues. A trigger installation can succeed without the trigger firing if permissions are incomplete.

The verification is the completion condition. The step is not done when the write call returns — it's done when the read-back confirms the expected state.

02

Surface failures at the point of action

When a step fails, the alert appears at that step — not at the end, not in the summary doc, not in a log the user never sees. The failure message names exactly what failed, explains the most likely cause, and gives the path forward in the same alert.

A failure message that says "An error occurred" is not a failure message. It is noise. A failure message that says "The CompetencyRegistry tab could not be created — verify you have edit access to [URL]" is a gate.

03

Retry in-place, never restart

When user input fails validation, the wizard stays open and presents the same prompt again. It does not exit, direct the user to a menu item, or require a full restart. Re-entry is in-place. The failure message appears before the next prompt — the user understands what they need to fix before they see the input field.

Three attempts is the standard ceiling. On the third failure, the wizard exits with a clear message explaining which menu item to use to complete the step. It never silently drops the requirement.

04

Never ask for what the system already knows

Before prompting the user to type a value, check whether that value already exists in the system. Course names live in the CompetencyRegistry tab and in Script Properties. Teacher name and email live in Script Properties from Module 1 setup. The admin root folder ID lives in Script Properties set at admin setup time.

Present found values to the user for confirmation — not for re-entry. Confirmation is one click. Re-entry is a correctness risk. The system should never require the user to type something it already has.

05

Make deferred state visible and persistent

If a step is deferred — because the user skipped it, because a file wasn't available, because a dependency wasn't met — that state must be visible every time the user opens the system until it's resolved. The menu item changes. The dashboard shows a banner. The status function reports it explicitly.

A "deferred" state that is indistinguishable from a "complete" state is a silent failure in a different costume. Deferred is acceptable. Silent is not.

How it looks in practice

The patterns

Concrete implementations of the five gates in Google Apps Script. These are not abstract guidelines — they are copy-paste starting points for any wizard step.

Pattern 1 — Verify after create

Create the resource, then read it back immediately. Gate blocks on mismatch before proceeding.

Tabs created — then verified before moving to next step Apps Script
// Create _createM2LightweightTabs_(ss); // Verify — read back immediately const missingTabs = ["LessonContext", "CompetencyRegistry", "AlignmentLog", "ReportRegistry"] .filter(t => !ss.getSheetByName(t)); if (missingTabs.length > 0) { ui.alert( "✗ Tab Creation Failed", "Could not create:\n\n" + missingTabs.map(t => " • " + t).join("\n") + "\n\n" + "Verify you have edit access to:\n" + ss.getUrl(), ui.ButtonSet.OK ); return; // Gate: do not proceed } // Only reaches here if ALL tabs verified present

Pattern 2 — In-place retry loop

User input is validated inline. Failure shows the exact problem and re-presents the same prompt. Wizard never exits on recoverable error.

Schedule input — validates inline, retries in-place, exits cleanly after 3 failures Apps Script
for (let attempt = 0; attempt < 3; attempt++) { const resp = ui.prompt( "Block Schedule" + (attempt > 0 ? " — Fix and Retry" : ""), FORMAT_HELP, ui.ButtonSet.OK_CANCEL ); if (resp.getSelectedButton() !== ui.Button.OK) return null; const { rows, errors } = parseSchedule_(resp.getResponseText()); if (errors.length > 0) { ui.alert( "⚠ Schedule Format Errors" + (attempt < 2 ? " — Please fix and retry" : " — Final attempt"), errors.map(e => " • " + e).join("\n"), ui.ButtonSet.OK ); if (attempt === 2) return null; // Clean exit after 3 failures continue; // Stay in loop — re-present same prompt } // Validation passed — confirm before writing const confirm = ui.alert("✅ Confirm", preview(rows), ui.ButtonSet.OK_CANCEL); if (confirm !== ui.Button.OK) continue; // Re-entry, not restart writeSchedule_(rows); return { rows }; // Success }

Pattern 3 — Read before asking

Check every available data source before prompting. Present found values for confirmation, not re-entry. Only ask when the system genuinely doesn't know.

Any manual step the user must take after the wizard runs is shown in the completion alert — not in the summary doc. The instructions are specific enough to follow without leaving the screen.

Pattern 5 — Persistent deferred state in the menu

A deferred step changes the menu item label until it's resolved. The user sees the gap every time they open the document — not just once in a completion alert they dismissed.

What to avoid

The anti-patterns

These are the failure modes that contextual gates are designed to prevent. Each one produces the same outcome: a user who doesn't know the system isn't working until they need it to work.

Silent success
The script ran without errors, therefore setup is done. No verification of the output state. Tabs created but empty. Triggers installed but not authorized. Registry imported but wrong format. The user sees a completion message and walks away. Fix → Gate 1: Verify output before declaring step complete.
Summary doc delivery
Instructions appear in the summary doc appended at wizard end. Teachers close the wizard when they see "Setup Complete." They don't read the page that was appended. The redeploy step, the manual trigger authorization, the CSV upload — all missed. Fix → Gate 2: Surface every required action in the completion alert, not the doc.
Exit on bad input
Validation fails and the wizard exits. The user has to find the menu item, re-open the wizard, navigate back to the failed step, and try again — with no memory of what they entered before. On the second attempt they often make the same mistake. Fix → Gate 3: Retry in-place. Stay in the loop. Show the error before the re-prompt.
Redundant entry
The wizard asks the teacher to type a value the system already has. Course names typed manually must match the CSV exactly — a trailing space breaks the dropdown silently. Teacher name typed again when Module 1 setup already stored it. Fix → Gate 4: Read before asking. Present found values for confirmation, not re-entry.
Silent deferral
A skipped step is indistinguishable from a completed step. The teacher defers the CSV import. The system marks Phase A complete. The competency dropdown is empty. The teacher logs a lesson and sees no competencies to select — no error, no indication, no path forward. Fix → Gate 5: Deferred state changes the menu label. Every open is a reminder.
Premature completion
The wizard offers a feature before the dependencies that make it useful exist. Phase B (warm-up generation) offered at the end of Phase A, before any evaluation history exists. Teacher sets up warm-ups, triggers run nightly against empty profiles, generic prompts are generated. Feels like it's working but isn't doing anything meaningful. Fix → Gate the offer on data readiness. Activate Phase B when M1 evaluation history exists.
Design decisions

The tradeoffs

Contextual gates add friction to the wizard flow. More alerts, more read-backs, more steps. These tradeoffs are deliberate.

DecisionTradeoff acceptedRationale
Verify after every create Extra read API calls. Slightly slower. A failed silent create caught at setup costs 2 seconds. Caught in the classroom costs a lesson.
3-attempt retry loop Three possible failures before exit. User can feel stuck. Most users succeed on retry 1 or 2. Clean exit on attempt 3 with a specific menu item is better than silent failure after attempt 1.
Inline redeploy instructions Long completion alert. Not dismissible quickly. The teacher who doesn't read it still saw it. The teacher who reads the summary doc would have seen it there — this just ensures both paths converge.
_gateAlert_ as no-op for progress messages Less visual progress feedback between steps. Alerts require clicks. Click fatigue is real. Progress messages that require no action don't need a dismiss button — they go to the log.
Menu label reflects deferred state Teachers see a warning item in their menu until they complete the step. That's the point. The warning is the behavior. Removing the warning requires completing the step.
Summary doc as record, not instructions Summary doc has less actionable content than before. The summary doc was never a reliable delivery mechanism for instructions. Making it a record (what was configured, when, by whom) makes it useful for its actual audience: the admin auditing the installation.
◈
The summary doc is not retired — it's repurposed. Summary pages still get appended to the manual on every setup run. But their job changes: they're an audit record for administrators, not a delivery mechanism for teacher instructions. The distinction matters. An admin reviewing what was configured six months ago needs the doc. A teacher configuring their classroom for next week needs the inline alert.
◈
This principle applies beyond setup wizards. Any Apps Script flow that creates something, deploys something, or configures something should apply the same gates. Module 1's AutoInstaller, Module 1's rubric extraction confirmation step, Studio Flow error handling — all of them have silent failure modes that contextual gates would catch. Script 28 is the proof of concept. The pattern scales to every deployment-adjacent flow in the system.
Before shipping

The checklist

Apply to every wizard step before shipping. If any item is unchecked, the step has a silent failure mode.

Gate 1 — Verification

Output is read back after every write. Tab created → tab read back. Trigger installed → trigger list checked. Row written → row count verified.
Verification failure blocks progress. The step is not marked complete if the read-back doesn't match the expected state.
Verification failure gives the URL. Every tab/spreadsheet verification failure includes the spreadsheet URL in the alert text.

Gate 2 — Failure messages

No failure message says only "An error occurred." Every failure names exactly what failed.
Every failure gives the most likely cause. Not just what happened — why it probably happened.
Every failure gives a path forward. Either "try again" or the exact menu item / manual step to resolve it.

Gate 3 — Retry behavior

Validation failure stays in the wizard. No prompt validation exits the wizard — it re-presents the same prompt.
Retry prompt shows the error before the input. The teacher knows what to fix before they see the field again.
Three-failure exit is clean and specific. After 3 attempts, wizard exits with the exact menu item to retry from.

Gate 4 — Data reuse

No value is asked for that the system already has. Script Properties, existing tab data, and config files are checked before any prompt.
Found values are presented for confirmation, not re-entry. One click to confirm. Not a text field.

Gate 5 — Deferred state

Every deferred step changes a menu item. The gap is visible on every document open until resolved.
Deferred state is stored in a distinct Script Property. Not inferred from absence — explicitly set as a known incomplete state.
Completing a deferred step clears the warning. The menu item reverts to the operational state label when the step is resolved.

The summary doc

No action items appear only in the summary doc. Every required action is in the completion alert. The summary doc records what was configured.
Manual steps are in the completion alert with exact steps. Not "see the summary doc." The steps are in the alert itself.
