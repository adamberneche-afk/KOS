3 New Tabs Scripts 22 + 26 No Studio Flows Additive — no M1 changes

Tab Overview

Three new tabs added to the existing Central Ledger spreadsheet. No existing tabs are modified.

LessonContext

One row per lesson submission. Written by Script 22 when the teacher submits the Lesson Context Form. The source of truth for what was taught, when, and why.

13 columns Written by: S22 Read by: S26, S27

CompetencyRegistry

One row per competency from the district framework. Set up once. Never written by any script after initial load — only read. Powers the form dropdown and the alignment log.

5 columns Written by: Manual / S28 Read by: S22, S26

AlignmentLog

Append-only. One row per lesson-competency pair — so one lesson with three competencies produces three rows. Accumulates automatically. Feeds end-of-term documentation export.

8 columns Written by: S26 Read by: dashboard, export

No other tabs

The lightweight build does not create WarmUpQueue, StudentProfiles, or ConceptMastery — those belong to the full Module 2 build. Module 1 tabs (ReviewQueue, STAGING_PIPELINE, etc.) are untouched.

M1 tabs: read-only from M2 perspective
◈
Naming convention: Tab names use PascalCase to match the Module 1 pattern (ReviewQueue, STAGING_PIPELINE, etc.). The exception is STAGING_PIPELINE, which is all-caps to signal infrastructure. New tabs follow the mixed-case convention of operational tabs.
LessonContext
Central Ledger · one row per lesson
Written by Script 22 on every Lesson Context Form submission. One row = one lesson = one day (or one multi-day unit, at teacher discretion). The row is never deleted — updated in place as status progresses from RECEIVED → ALIGNMENT_LOGGED → FRAME_GENERATED (or SUPERSEDED/ERROR at any point). PUBLISHED, mentioned in earlier drafts of this lifecycle, has no described or built mechanism anywhere in this repo — left undocumented rather than invented.
ColumnTypeWriterDescription
── IDENTITY ──
lesson_id String S22 Auto-generated UUID. Format: LES-{YYYYMMDD}-{4hex}. Primary key. Used in AlignmentLog foreign key.
teacher_email String S22 Authenticated submitter email. Pulled from Session.getActiveUser() at form submit — not a form field. Used for routing to teacher-specific dashboard view.
submitted_at DateTime S22 Server timestamp at row write. ISO 8601. Distinct from lesson_date — a teacher may submit Friday's lesson plan on Thursday evening.
── LESSON CONTENT (from form) ──
lesson_date Date S22 The date this lesson is taught. Form field — teacher-entered. YYYY-MM-DD. Used as display label in all downstream views and the alignment log.
period_or_class String S22 Optional. Period name or class identifier (e.g. "Period 3", "AP Lang"). Allows a teacher with multiple sections to submit separate lesson contexts for the same date. Nullable — single-section teachers leave blank.
activity_description Text S22 What students are doing today. Plain prose. Free-form. Not processed by any script until frame generation — consumed as-is by S27 (Lesson Frame Generator) into the "Today's Activity" section of the Lesson Frame Document.
learning_objective Text S22 What students can do by end of lesson that they couldn't at the start. Teacher's own language. Becomes the anchor for the Lesson Frame Document and the AlignmentLog objective field.
key_vocabulary Text S22 Comma-separated terms. E.g. "irony, dramatic irony, situational irony". S22 trims whitespace but does not validate against any vocabulary list. Stored as-written.
prior_lesson_connection Text S22 What last lesson covered that this one builds on. Free-form prose. Nullable — first lesson of a unit may leave blank. Used in Lesson Frame Document to make the learning progression explicit.
competency_ids Text S22 Comma-separated competency IDs from CompetencyRegistry. E.g. "ELA-W-1,ELA-W-3". S22 validates each ID exists in CompetencyRegistry before writing — unknown IDs trigger a validation error returned to the form.
◈
Correction: earlier drafts of this table documented a warm_up_generated Boolean column (writer: S24) here. It does not exist in the built schema and never has — LessonContext and WarmUpQueue are unrelated subsystems (S24's findLesson_() reads this tab only to seed nightly warm-up generation; it never writes back to it). Removed rather than left to mislead. See 27_LessonFrameGenerator's "Suggested Warm-Up" placeholder section for how this gap is actually handled at frame-generation time.
── LESSON FRAME (S27) ──
frame_doc_id String S27 Google Drive file ID of the generated Lesson Frame Document. Self-healing column — added to the header row on first use by any deployment predating this feature. Null until FRAME_GENERATED.
frame_doc_url String S27 Shareable URL for the Lesson Frame Document. This is the value S22 returns as frameDocUrl to the teacher dashboard, which opens it via the client's existing (previously dormant) window.open() hook. Null until FRAME_GENERATED.
frame_generated_at DateTime S27 Timestamp when Script 27 successfully created the Lesson Frame Document. Null until processed.
── STATUS + PIPELINE ──
status Enum S22, S26 Lifecycle state of this lesson row. See enum values below.
alignment_logged_at DateTime S26 Timestamp when Script 26 successfully wrote AlignmentLog rows for this lesson. Null until processed. S26 uses this as its processed check — it skips rows where this field is populated.
error_notes Text S22, S26 Human-readable error detail written by any script on validation failure. Null on success. Visible in admin health check. Never shown to students.
status enum
RECEIVED→ S22 has written the row. S26 has not yet run.
ALIGNMENT_LOGGED→ S26 has written AlignmentLog rows for this lesson.
FRAME_GENERATED→ S27 has created the Lesson Frame Document.
SUPERSEDED→ Teacher resubmitted the same lesson (same teacher_email + lesson_date + period_or_class); a new row exists with a new lesson_id. S26 skips SUPERSEDED rows.
ERROR→ A script encountered a failure. See error_notes. Retryable.
◈
Why ALIGNMENT_LOGGED not COMPLETE? The lightweight build has two distinct downstream steps: alignment logging (S26) and frame generation (S27) — both built, called back-to-back synchronously inside onLessonContextSubmit_(). Using separate status values still means either step's failure is independently visible: the status column tells you exactly where each row got to in the pipeline, and a row can rest at ALIGNMENT_LOGGED if frame generation itself failed non-fatally (see error_notes).
CompetencyRegistry
Central Ledger · one row per competency · set up once
The source of truth for the competency framework. Set up once from the district framework at the start of the year. Never modified by operational scripts — only read. A teacher with multiple courses may have multiple subjects in the same registry, filtered by the subject and teacher_email columns.
ColumnTypeWriterDescription
competency_id String Manual / S28 Primary key. Short human-readable code. E.g. ELA-W-1, SCI-INQ-3. No spaces. Validated against this registry when LessonContext form is submitted. Must be unique within the sheet.
competency_text Text Manual / S28 Full competency statement as written in the district framework. Pasted verbatim. This is the text that appears in the Alignment Log and any documentation exports.
subject String Manual / S28 Subject area. E.g. ELA, Science, History. Used to filter the Lesson Context Form dropdown to show only relevant competencies to each teacher.
grade_band String Manual / S28 Grade range. E.g. 9-10, 11-12. Nullable for frameworks that span all grades. Secondary filter for form dropdown.
strand String Manual / S28 Competency category within subject. E.g. Writing, Reading, Speaking & Listening. Used in AlignmentLog coverage report to group competencies by domain.
teacher_email String Manual / S28 Optional. If populated, this competency is only surfaced to this teacher's Lesson Context Form dropdown. Null = available to all teachers with matching subject. Enables subject-specific frameworks per teacher without separate sheets.
active Boolean Manual Default TRUE. Set to FALSE to retire a competency without deleting it. Inactive competencies are excluded from the form dropdown but remain in AlignmentLog history. Preserves referential integrity.
◈
teacher_email is the lightweight alternative to a separate sheet per teacher. If you later run Module 2 for colleagues, their competency frameworks can coexist in the same registry tab, filtered by their email. No schema change required.
AlignmentLog
Central Ledger · one row per lesson-competency pair · append-only
Script 26 writes one row here for every competency ID in a LessonContext row. A lesson with three competencies = three AlignmentLog rows, all sharing the same lesson_id foreign key. Append-only — rows are never updated or deleted. This is the artifact that becomes term-end documentation.
ColumnTypeWriterDescription
── IDENTITY ──
log_id String S26 Auto-generated UUID for this specific log row. Format: ALG-{YYYYMMDD}-{4hex}. Not the lesson ID. Used if rows ever need to be referenced individually (e.g. in a future export function).
lesson_id String S26 Foreign key to LessonContext.lesson_id. All AlignmentLog rows produced from one lesson submission share the same lesson_id. Enables JOIN-style lookups between tabs.
logged_at DateTime S26 Server timestamp when S26 wrote this row. ISO 8601. Used for audit trail and as the sort key when generating coverage reports chronologically.
── DENORMALIZED LESSON FIELDS (for readable exports) ──
lesson_date Date S26 Copied from LessonContext at write time. Denormalized so the AlignmentLog tab is self-contained and readable without a JOIN. This is the field that appears in the end-of-term documentation report.
teacher_email String S26 Copied from LessonContext. Denormalized. Enables filtering the alignment log by teacher without looking up the lesson_id in LessonContext first.
learning_objective Text S26 Copied from LessonContext. The human-readable description of what this lesson was for. Makes the log row meaningful in isolation — an administrator reading the export sees what was taught, not just a competency code.
── COMPETENCY FIELDS ──
competency_id String S26 The single competency this row represents. Foreign key to CompetencyRegistry.competency_id. One row per competency per lesson — multiple competencies produce multiple rows.
competency_text Text S26 Copied from CompetencyRegistry at write time. Full competency statement. Denormalized for the same reason as learning_objective — the export document should be self-contained, not dependent on another tab.
strand String S26 Copied from CompetencyRegistry. Used in the coverage report to group log rows by competency domain (Writing, Reading, etc.) and identify which strands have and haven't been addressed.
◈
Why denormalize? The AlignmentLog is the export artifact. When an administrator asks for documentation of competency coverage, you want to be able to filter the AlignmentLog tab directly in Sheets and share it — not explain that they need to cross-reference two other tabs to understand what they're reading. Denormalization here is a deliberate product choice, not a schema mistake.
◈
Append-only is the rule. S26 never updates or deletes AlignmentLog rows. If a teacher resubmits a lesson context with corrected competency IDs, S26 appends new rows and notes the correction in LessonContext.error_notes. The old rows remain for audit integrity. A future admin function can filter by logged_at to use the most recent mapping per lesson_id.

Implementation Notes for Scripts 22 + 26

Decisions that should be made before writing a line of code.

TAB CREATION Script 28 (setup wizard extension) should be the one that creates all three tabs with the correct headers. Scripts 22 and 26 should detect missing tabs and throw a clear error rather than attempting to create them — keeps setup concerns separated from operational concerns. For the lightweight build before S28 exists, a manual setup function in S22 is acceptable.
TRIGGER — S22 onFormSubmit trigger installed by S22's self-registering trigger pattern (same as S05 in Module 1). The Lesson Context Form's submit fires S22. S22 validates, writes to LessonContext, sets status RECEIVED, then calls S26 directly (not via a queue) — lightweight build has no need for queue decoupling at this stage.
TRIGGER — S26 Called directly by S22 after a successful LessonContext write. Also installable as a standalone time-based trigger (every 5 min) to catch any RECEIVED rows that S22 dropped on. S26 reads all LessonContext rows where alignment_logged_at is null and status is RECEIVED — idempotent, safe to run repeatedly.
VALIDATION S22 validates: (1) lesson_date is a valid date and not in the past by more than 30 days, (2) learning_objective is non-empty, (3) every ID in competency_ids exists in CompetencyRegistry with active=TRUE. Validation failure writes status=ERROR and error_notes, and returns a user-facing error to the form response. Does not write to AlignmentLog.
DEDUP If a teacher resubmits the same lesson (same teacher_email + lesson_date + period_or_class), S22 creates a new row with a new lesson_id rather than updating the original. The old row's status becomes SUPERSEDED — now in the enum above. S26 skips SUPERSEDED rows. This preserves history and avoids update-in-place complexity in the lightweight build.
CONFIG Module 2 config values go in the existing _CONFIG tab (Script 19 pattern). New keys: M2_LESSON_CONTEXT_FORM_ID, M2_ENABLED, M2_DEFAULT_SUBJECT. Same getConfig_() reader — no new config infrastructure needed.
◈
Column order matters. Sheets doesn't enforce schema — the column positions in the actual tab must match what the scripts expect. Establish a canonical column order now and document it as the header row. Both S22 and S26 should write by column name (using a header lookup pattern) rather than by hardcoded column index, same pattern as Module 1.

Module 2 Full Build — Additional Tabs

The following tabs are created during Module 2 Full Build (warm-ups). They are not part of the Lightweight build. Full schemas in CAS_M2_WarmUp_Schema.html.

PacingGuide — 16 columns — read-only after import

20-unit pacing guide imported from PacingGuide_CAS_Context.json by Script 29. Key fields: lesson_unit_id · approx_start · approx_end · warmup_anchor · prior_lesson_connection · competency_ids per course. Drives unit resolution for shadow matrix and warm-up anchor seeds for Flow 3.

CompetencyRubrics — 8 columns — 221 rows — read-only after import

221 competency rubrics imported from CompetencyRubrics.json by Script 30. Extracted from two Canvas Common Cartridges (courses 8175 + 8177). Key fields: competency_id · demonstration_indicators (JSON array) · skill_questions (JSON array, avg 4.9 per competency). Script 24 embeds rubrics in WarmUpQueue snapshots via addRubricsToSnapshot_(). Resolves sparse context — Flow 3 always has structured skill questions regardless of lesson context detail.

TeacherMatrix — new column: competency_ids

The Teacher Matrix (Module 1, Script 16) gets one new column added by Script 31: competency_ids (comma-separated IDs, e.g. "8177-47,8177-52"). Run addCompetencyIdsColumn_() once. The teacher tags each assignment with the competencies it addresses. Script 31 reads this at 3:05am to compute per-student competency coverage from completed work artifacts.

CompetencyRubrics — July 2026 enrichment

Three new fields added to every rubric entry following extraction from both VDOE official standards files.

Field Coverage Notes
sol_correlations 197 / 221 Subject-keyed SOL code object. English: 117, History & SS: 75 (normalized from singular/plural variants), Math: 16, Science: 12. Sources: 8175 printable version (uploaded) + 8177 printable version (embedded in Canvas management cartridge at web_resources/Uploaded Media/). 24 CTSO/WBL tasks have no SOL by VDOE design.
definition 197 / 221 Official VDOE definition text (the "Demonstration includes..." block). Previously only available as demonstration_indicators array — now also present as the original prose form.
required 221 / 221 "R" for required, "O" for optional. Optional tasks carry "(O)" in the VDOE task number column. 8175: 6 optional. 8177: 6 optional. Script 31's artifact competency bridge should weight required competencies more heavily than optional ones in coverage calculations.
