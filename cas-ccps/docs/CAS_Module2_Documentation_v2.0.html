What this module does

The prerequisite for instruction

Module 1 automates the prerequisite for student submission. Module 2 automates the prerequisite for instruction — the documentation and alignment work that happens before class, and the cognitive priming that happens as students walk in.

◈
Two independent builds. The lightweight build is deployable today and produces immediate value: automatic competency alignment documentation from lesson context submissions, with a term-end report generated on demand. The full warm-up build layers on top and adds student-specific cognitive entry points generated overnight, scored nightly by AI, and feeding a longitudinal student profile. Either build runs independently. The full build requires the lightweight build to be in place first.
◈
Module independence from Module 1. Module 2 adds tabs and scripts to an existing Module 1 installation. No existing scripts are modified. Module 2 can be disabled by setting M2_ENABLED = false in Script Properties. Module 1 continues running identically.

Architectural decisions

  • NO QUEUE Script 22 calls Script 26 directly. No queue needed — no Studio Flows, no async latency. The entire submission pipeline completes synchronously within one web app request. The 5-minute backfill trigger catches any silent failures.
  • MODAL IN S07 Lesson Context form lives inside the Teacher Dashboard. Same deployment, same URL, teacher identity injected server-side from Script Properties. Competency dropdown filtered by course — two tabs, sorted by task number, discovered dynamically from the registry.
  • APPEND-ONLY LOG AlignmentLog rows are never updated or deleted. Resubmissions append new rows; the old LessonContext row is SUPERSEDED. The log is an audit record, not a live state table. Reports filter by logged_at for the most recent mapping per lesson.
  • DENORMALIZED AlignmentLog copies lesson fields at write time. The tab is self-contained — an administrator reading an export sees a complete record without cross-referencing other tabs.
  • PER-COURSE DUPES Foundation competencies (tasks 1–38) are logged separately per course. 8175-5 and 8177-5 are distinct IDs. Each course's coverage is independently tracked and reported in separate sections of the AlignmentReport. Intentional and settled.
  • MULTI-TEACHER Each colleague gets their own Central Ledger installation. Script 28 (setup wizard extension) handles cloning. M2_ENABLED defaults to false — explicit opt-in required per installation.

Block schedule awareness

Classes meet on odd or even calendar days (derived from date parity). First period meets daily. Period day types configured once in the ClassSchedule tab. Holiday handling is implicit — if no LessonContext is submitted for tomorrow, no warm-ups are generated regardless of the schedule.

◈
Throughput at 150 students across 4 periods: ~40 students per period. Flow 3 at 40 students × 30s = ~2–4 minutes with Studio parallelism. Script 25 evaluation at 40 doc opens × 2s = ~80 seconds per period batch. All stages complete within the 3am–6am window. Batch writes in Script 24 (single setValues() per period) keep queue-build time under 10 seconds total.

Ambient onboarding — shadow matrix

Derived from the KOS probabilistic state matrix pattern. The system quietly learns which warm-up archetype produces the best engagement trajectory for each student at the granularity of each unit — without asking the teacher anything. The shadow matrix lives as a JSON field in the teacher profile row of the StudentProfiles tab, updated nightly by Script 23.

◈
Two confidence layers: Within-unit confidence builds across warm-ups in the current unit (history length / 8 expected warm-ups per 3-week unit). Cross-unit confidence is a decayed weighted average across all prior units using a 0.85 decay factor — recent units weighted more heavily. When cross-unit confidence crosses 0.75 for a given student × archetype combination, Script 25 sends the teacher a batched email digest. The teacher can reply OVERRIDE to keep the default selection; otherwise the system locks to the confident archetype for that student's remaining warm-ups in the unit. At 3:30am, getStudentProfileSnapshot_() in Script 23 computes a pre-formatted shadow_archetype_note string for each student — e.g. "Shadow matrix suggests PARADOX (72% confidence, 5 warm-ups in unit S1-U3, trend: rising)" — and embeds it in the student_profile_snapshot JSON on the WarmUpQueue row. Flow 3 reads it as the {shadow_archetype_note} placeholder in the Mode A system prompt. Null when confidence is below threshold. Computed once at snapshot time — no Sheets reads at generation.
◈
Pacing guide as the unit clock: Script 29 resolves any lesson date to its pacing guide unit by matching against approx_start and approx_end date ranges. The 20-unit pacing guide covers the full academic year. The shadow matrix resets its within-unit confidence at each new unit boundary while retaining cross-unit history. The teacher never tags lessons with unit names — the date is the only input.
◈
Warm-up anchor — two-mode generation: Each pacing guide unit contains a teacher-authored warmup_anchor seed prompt. When present, Flow 3 runs in Mode A: personalizing the anchor for each student rather than generating from scratch. The anchor guarantees pedagogical quality; Flow 3 applies the archetype angle and student personalization. When absent (pacing guide not yet imported), Flow 3 runs in Mode B: generative from the lesson context and competency rubrics alone. Both modes are valid — Mode A produces consistently higher quality.
◈
Competency rubric enrichment — weak point 2 resolved: Each selected competency's rubric (from Script 30) is embedded in the WarmUpQueue lesson context snapshot via addRubricsToSnapshot_(). The rubric includes 1–11 skill questions pre-mapped to the four archetypes via archetype_question_map. Flow 3 receives structured question options for every competency regardless of how minimal the teacher's lesson context submission is. A teacher who submits a one-line objective still gives Flow 3 enough material for a quality prompt — the competency rubric carries the pedagogical substance.

Artifact-based competency tracking — Script 31

Script 31 runs at 3:05am — between Script 23 (class-level baseline) and Script 25 (evaluation). It reads STAGING_PIPELINE for COMPLETE assignments, joins to the Teacher Matrix's new competency_ids column, and writes per-student competency coverage to StudentProfiles. The result: competencies_addressed reflects work actually produced, not just lessons attended. The warm-up competency gap computation in Script 24 becomes genuinely per-student.

◈
The artifact evidence model: Completion of a work artifact = demonstrated competency exposure. A student who was present but disengaged has no artifact. A student who was absent but completed makeup work has one. Script 31's merge is strictly additive — it never removes competencies from a student's profile, only adds. The Teacher Matrix needs one new column: competency_ids (comma-separated IDs). Run addCompetencyIdsColumn_() from Script 31 once to add it. Run installArtifactSyncTrigger_() to install the 3:05am trigger.

Flow 5 — Bridging Flow

Flow 5 generates a 2–3 sentence connector between a student's most recent warm-up response and today's lesson. It runs before Flow 3 on the same PENDING queue row. Script 24 embeds the student's prior response (flow5_prior_response, capped at 800 chars) in the per-student lesson context snapshot at 3:30am. Flow 5 reads this at 6am and writes a bridge paragraph to bridge_output (WarmUpQueue column 21). Flow 3 prepends it to the warm-up doc when present. Students with no prior history receive no bridge — strictly additive.

◈
Temperature 0.4 — lower than Flow 3's 0.7. Flow 3 generates — it needs variation and creative framing. Flow 5 connects — it needs accuracy. A bridge that misrepresents what the student wrote is worse than no bridge. Lower temperature keeps Flow 5 close to what the student actually expressed. Max tokens: 150. One paragraph. Full specification in CAS_Flow3_Flow4_Specification.html v1.2.

Setup wizard — contextual gates

Script 28 implements the Contextual Gates design philosophy throughout. Every setup step verifies its own output before declaring success. Every failure surfaces at the point of action with an exact path forward. No instruction is deferred to a document the teacher won't read. The teacher never types something the system already knows. A "complete" state means verified complete — not "the script ran without errors." This philosophy is documented in full in CAS_ContextualGates_DesignPrinciples.html and applies to every deployment-adjacent flow in the system.

Cron health monitoring — weak point 3 resolved

Each cron stage writes a health stamp to Script Properties on completion. The subsequent stage reads that stamp at startup and checks whether it's within the expected window. If a stage ran more than 45 minutes ago, Script 25's _checkCronHealth_() sends one email alert to the teacher (or admin) and sets a flag to prevent repeat alerts for the same stale event.

◈
Health stamps written: M2_STAGE1_LAST_RUN / M2_STAGE1_STATUS by Script 23 · M2_STAGE2_LAST_RUN / M2_STAGE2_STATUS by Script 25 · M2_STAGE3_LAST_RUN / M2_STAGE3_STATUS by Script 24. Health checks are non-fatal — the current stage continues regardless. The alert is the signal, not the gate. A teacher who sees the alert knows to check the execution log and can manually trigger the missed stage from the Script Editor.
