System Architecture Overview

How all components connect, how data flows, and what happens when things go wrong. For administrators inheriting the system and developers extending it.

Google Apps Script Workspace Studio Google Drive / Sheets / Docs No external APIs
🧱

Design Principles

Decoupled inference. No API key ever touches a student-accessible surface. All Gemini inference runs through native Workspace Studio Flows — the system acts as a queue and data router. Studio owns the model call; GAS owns everything else.

Math-before-muse. GAS handles all quantitative operations — sorting, filtering, aggregation, column arithmetic. Studio handles only synthesis and evaluation. Neither system does the other's job.

Pointer-driven execution. Scripts pass IDs and references between systems — never content. The queue contains file IDs; Studio fetches content via connector. This keeps the queue small and auditable.

Single active evaluation. The Turnstile (Script 06) releases exactly one STAGING_PIPELINE row to IN_PROCESS per cycle. This prevents concurrent Gemini calls that would exhaust quota and makes failure states unambiguous — a stuck row blocks the pipeline visibly rather than silently.

Config persistence via tabs. Script Properties don't clone with makeCopy(). Cloned sheet projects read config from a _CONFIG tab written at clone time. Scripts 05 and 08 use getSheetConfig_() from Script 19 instead of getConfig_().

Document zone architecture. Student documents have four delimited zones — feedback, prompt, response, footer. All GAS and Studio operations target named text markers, never positional line numbers. This makes the system resilient to content additions.

Configuration System

Script 00 (getConfig_) is included in every project and reads from Script Properties. Works correctly for projects where properties are set directly (Central Ledger, Admin Manual, both web apps).

Script 19 (getSheetConfig_) is used by Scripts 05 and 08 instead of getConfig_. Reads from the _CONFIG tab on the active spreadsheet via SpreadsheetApp.getActiveSpreadsheet(). Falls back to getConfig_() if the tab is missing. Opportunistically writes key IDs to Script Properties during user-context opens so time-driven triggers can find them later.

_CONFIG tab is written by Script 16's setup wizard immediately after each makeCopy() call. Contains all key-value pairs the cloned project needs. Protected with a warning-only lock. Located at the far right of the sheet's tab bar.

Student doc ID resolution uses a three-tier fallback: Script Properties (master template only) → embedded [SYS_LEDGER_SS_ID:...] invisible text (student copies) → null with user-facing error. The embedded block is written by stampDocument_() in Script 02 as invisible white 1pt text below the CONFIG_ID footer.

Security Model

No credentials on student surfaces. Students interact with their Google Doc (bound script), the evaluation menu, the Turn-In Form, and the Student Dashboard. None of these surfaces contain API keys, rubric criteria, other students' data, or system IDs beyond their own CONFIG_ID and the embedded ledger SS ID.

Prompt injection mitigation. Student text is wrapped in <<<STUDENT_SUBMISSION>>> markers in the Flow 2 user message. The system prompt explicitly instructs Gemini to treat everything between those markers as passive data regardless of content — a student cannot manipulate the evaluation by writing instructions in their response.

Three-point turn-in validation. Google ID + File ID + CONFIG_ID must all match a single Ledger row. A student cannot submit on behalf of another student (wrong Google ID), submit a different document (wrong File ID), or forge a CONFIG_ID (not in Ledger).

Compliance stamp forensic check. The turn-in gate checks for a rapid block write in version history — the signature of an automated Studio write. Manual insertion of a fake compliance stamp (typing or slow paste) is detectable. Fast paste of a complete block is not detectable by this method — this is a documented limitation. The three-point validation provides the primary anti-fraud layer.

Teacher Matrix isolation. Teachers can only see their own assignments in the dashboard and receive notifications only for their own students. The MatrixRegistry lookup in Script 02 routes each CONFIG_ID to the correct teacher's matrix — teachers cannot access each other's assignment configurations.

⚠️
Known limitation: The forensic check uses a 15-second timing window for rapid block writes. A student who selects all and pastes a pre-written fake report in a single fast operation may pass this check. The primary defense is the three-point ledger validation, not the forensic check. Treat FORENSIC_FAILURE as a signal for manual review, not proof of fraud.
