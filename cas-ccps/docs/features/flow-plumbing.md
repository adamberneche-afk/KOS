# Flow plumbing added after the first deployment (scripts 37-40)

Moved from `cas-ccps/README.md` on 2026-11-21 (meta/AUDIT_STRUCTURE_2026-11-20.md,
4.2); the README's "Features" table links every file in this folder.

Cross-module infrastructure rather than a module — every script below is
bound to `cas-ccps:central-ledger`, and every one exists because the first
real deployment found that Workspace Studio can do less than the design
assumed. See `HISTORY.md`'s deployment sections for the walls each one works
around. (This paragraph said "all four" while the table held four rows; it has
grown to seven since, which is exactly the kind of count worth not writing
down twice.)

| Script | What it does | Run it via |
|---|---|---|
| `35_FlowPreflightAndCanary.js` | Structural preflight plus the two canaries. `runFlowPreflightCheck()` verifies what has to exist before a Flow can match anything — the tabs, the four time triggers (a duplicate counts as a failure, not a pass), the required Script Properties, the self-healing tabs — and says which of the four questions each finding answers. The canaries verify the Apps Script half with the Flow deliberately stubbed, and say so in their own log. `runFlowPreflightCheckNow()` and `runFlow2CanaryNow()` run the same from the Ledger's editor and show the result in a dialog (the canary's names its first failed stage and the clean-up call). | `runFlowPreflightCheck()`, `runFlow2Canary()` |
| `37_FlowInputBuilder.js` | **The Flow 2 redesign.** Resolves Ledger → MatrixRegistry → TeacherMatrix in Apps Script and materializes one flat literal `FlowInput` row, so the Flow reads a single row and needs no custom step and no variable spreadsheet target. `harvestFlowInputResults()` applies Studio's result back: the feedback, the Ledger's result columns, one `EvaluationLog` row per result (since 2026-10-23; no student text), and `ERROR_EVALUATION` on the staging row when the result can't be used. A `READY` row Studio leaves unanswered for 12 minutes (the lane timeout) is restarted: `ReadyStatus` cleared, then set `READY` on the next run, at most twice, then `ERROR_NO_ANSWER`, which blocks only that submission; a re-queued or resubmitted submission whose row still waits restarts it at once. The count and time are in `ReArms`/`ArmedAt`, appended at the end (2026-11-14). Since 2026-11-15 a result is checked before anything reaches the student (`_fiCheckResultShape_`): a parseable last `[MILESTONE_OUTCOMES]` line, only `MET`/`PARTIALLY_MET`/`NOT_MET`, the row's milestones, one compliance stamp, and a stamp the passing rule agrees with; a malformed one is never delivered, is re-armed once on the same counters, then `ERROR_MALFORMED_OUTPUT` ("Couldn't be checked"). One answer in an earlier row of the same doc (a hash, never the text) is a duplicate write: a dates-only row in `Flow2Duplicates`, the newer row delivered, an unharvested older copy re-armed; `showSetupStatus()`, the overnight check and the Teacher Dashboard's Flow 2 light warn for 7 days. Studio's Update rows step must match on `StagingRowRef` (column B). Since 2026-11-16 each prompt carries a run key of its own and the template's version (`f2-` + 8 hex), which the answer copies back in a `[RUN_INFO: {...}]` line along with the model it says it is; the harvest strips the line and records in `EvaluationLog` the CodeVersion (deploy marker), PromptVersion, PromptHash, RunCheck (`OK`, `NO_RUN_INFO`, `RUN_INFO_NOT_JSON`, `RUN_KEY_MISMATCH`, `PROMPT_MISMATCH`, `OLDER_PROMPT`) and ModelReported. A failed check is recorded and logged; a `RUN_KEY_MISMATCH` (another row's answer) is also held back since 2026-11-19, set aside like a malformed result (re-armed once, then `ERROR_MALFORMED_OUTPUT`). Two time jobs (both every minute; the harvest was every 5 before 2026-11-14), run by the Ledger cycle (`64`) once `installLedgerCycle()` has taken them over. | `installFlowInputTriggers()` once (or the Ledger cycle); then automatic. `removeFeedbackCommentsPosted(from, to)` lists the feedback comments this account posted on FlowInput's docs in a time window (a dry run); add `true` to delete them (2026-11-15, after a Studio Test run re-graded every row). `repostMissingFeedback()` lists docs whose newest row is harvested but has no feedback comment since it was built (the cleanup took the only one); `repostMissingFeedback(true, [refs to leave out])` posts them as the harvest would |
| `38_LedgerSchemaGuard.js` | Detects and safely repairs Ledger column drift — the live Ledger had shifted so `LEDGER.TEACHER_EMAIL` read a person's *name*, silently breaking the MatrixRegistry hop with no error. Backs the tab up before mutating, and refuses when it can't verify the repair is safe. | `checkLedgerSchema()`, then `repairLedgerSchema()` if it reports drift |
| `39_FlowFixtures.js` | Persistent dummy rows at all five flows' trigger conditions, so a flow has something to match instead of reporting a green "Run Completed" over zero rows. Namespaced `VDOE-FIXTURE-*` / `WUQ-FIXTURE-*` / `fixture-*@example.invalid`, deliberately separate from the canaries' namespace. | `installFlowFixtures()`, `checkFlowFixtures()`, `removeFlowFixtures()`; `removeFlow2Fixture()` for Flow 2's alone (2026-11-15: `cleanUpFlow2Canary()` clears canary rows only, and says when a fixture row is left); `installFlow2Fixture(2)` seeds two rows READY in one write (two assignments, two docs, StagingRowRef `FIXTURE` and `FIXTURE-2`) to test Studio's grouped runs, and `checkFlow2Fixture()` says whether each got its own feedback; `installFlow2ReflectionFixture(pairs)` (2026-11-19, D19) seeds pairs of rows identical but for a reflection that claims a success metric the made-up response leaves out (default 3 pairs, 2 Studio runs each, at most 5), and `checkFlow2ReflectionFixture()` says whether any pair was graded differently and whether the claim was credited |
| `39b_Flow2Provenance.js` | **What runs Flow 2, recorded and watched** (2026-11-16). `StudioConfig`: the operator's record of Studio (From, Flow, Step, Model, Settings, Note), rows only added; the harvest (37) stamps the model in effect for Flow 2's Ask Gemini step on each `EvaluationLog` row (`ModelConfigured`), and `showSetupStatus()` warns when Flow 2's record is missing, names no model, or is over 14 days old. The daily drift probe: Flow 2 grades the same fixture text once a day (a FlowInput row with StagingRowRef `PROBE`, which the harvest leaves alone); the next run records its stamp, outcomes, shape, length band, run check, reported model and our code and prompt versions in `Flow2Drift`, and a model or shape change with no change of ours is flagged as a platform change in the overnight email and `showSetupStatus()` for 3 days; an unanswered probe is flagged at once. | `installStudioConfig()` once (seeds 11-13 to 11-15), then `recordStudioChange({ flow, step, model, settings, note, from })` per change and `confirmStudioConfig()` after a check; `installFlow2DriftProbe()` once (a daily trigger, about 6 a.m.); `removeFlow2DriftProbe()` |
| `39c_ZeroShotAnswers.js` | **Generated** by `tools/cas-ccps/build-zero-shot-answers.js` from `curriculum/zero-shot/<lesson key>.txt`: each lesson's cold answer, what a general-purpose chatbot writes when a student pastes the whole assignment (written 2026-11-20 from the student-facing prompt alone, never the rubric). Made-up text. |
| `39d_ZeroShotFixture.js` | **The zero-shot test** (2026-11-20): which lessons a student could pass by pasting the assignment into a chatbot. `installZeroShotFixture(count)` sends the next `count` lessons' cold answers (default 10, at most 25) through Flow 2 as fixture rows (`VDOE-FIXTURE-Z<n>`, `FIXTURE-3nn`), graded on the whole lesson's goals and definition of done, with fixture competency IDs so no real evidence is written; `checkZeroShotFixture()` records each answered lesson in the `ZeroShotResults` tab (outcomes, stamp, first goal met, all met, and the lesson's Forms/Slides/Sheets part, which a pasted answer can't make) and logs the tally; the next install skips recorded and waiting lessons. One Studio run per lesson, 67 in all. `removeFlow2Fixture()` clears the rows; the results stay. |
| `40_FlowPrompts.js` | Every reusable flow prompt as a constant plus a `FlowPrompts` tab, so a prompt change is a `clasp push` and one function run instead of a hand-paste into each Flow. Flow 2 resolves through `15b`'s existing constant rather than carrying a second copy. The rest are generated by `tools/cas-ccps/generate-flow-prompts.js`: Flows 3 and 4 from `docs/CAS_Flow3_Flow4_Specification.html`, Flow 1 from [`docs/RUBRIC_EXTRACTION_FLOW.md`](../RUBRIC_EXTRACTION_FLOW.md) (which also has the flow's steps), Flow 6 from `docs/TURN_IN_CHECK_FLOW.md`. Flow 5's prompt was removed 2026-11-20. `substituteFlowPrompt_()` leaves unmatched placeholders standing — `{{STUDENT_TEXT}}` stays unfilled on purpose, since student response text must not enter the central Ledger (FERPA). | `syncFlowPromptsToSheet()`, `checkFlowPrompts()` |
| `41_WarmUpFlowBridge.js` | **The Flows 3/4/5 port** (Flow 5, the bridge, retired 2026-11-01: Flow 3 writes a returning student's lead-in, answering `LEAD-IN:` then `WARM-UP:`, and the harvest splits them and drops a lead-in that fails its check without touching the warm-up; a row 24 left at `PENDING_BRIDGE` goes to Flow 3), same two-phase shape as 37: materializes `Flow3Input`/`Flow4Input`/`Flow5Input` rows and harvests a shared `WarmUpFlowReturn` tab, so Studio makes only the Gemini call. Carries the archetype decision table and the warm-up document construction ported from the two blocked custom steps that held real logic; fills each prompt's placeholders through `WFB_PROMPT_VARS` (field and placeholder names differ, and before 2026-10-10 most went unfilled), records the chosen archetype and, since 2026-10-23, `delivered_at` on the WarmUpQueue row (`25` records `answered_at`), and holds the cross-unit archetype lock off unless `PIVOT_ARCHETYPE_LOCK` enables it; writes at most 10 input rows per 5-minute run (Studio drops runs when many rows change at once) and writes a `READY` job with no return after 30 minutes again as a new row, the old one marked `RETRIED`, at most twice; reuses `25_WarmUpWriter.js`'s existing `evaluateWarmUpDoc_`/`writeFinalScores_`/`writeFeedbackToDoc_`/`writeRegistryScores_` rather than copying the three steps that duplicated them. Leaves the WarmUpQueue status machine untouched, so Scripts 23/24/25 needed no edits. | `installWarmUpFlowTriggers()` once (or the Ledger cycle); then automatic. `checkWarmUpFlowLiveness()`, `runWarmUpFlowCanary()` The shape check (2026-11-20) refuses a warm-up that is Flow 3's prompt, its wording, a summary of its instructions ("the provided document …"), a competency code or a list, and, when it doesn't keep the anchor whole, one that neither asks a question nor ends in a direction asking for an answer ("Think about … and describe …"); a refused one goes out as the teacher's anchor, noted `ANCHOR_FALLBACK`. |
| `42_FlowBuildSpec.js` | Generates the `FlowBuildSpec` tab an operator builds a Flow from: every tab, column number, header, trigger condition, prompt key and ownership rule for Flows 1-4, **derived from the constants the code reads**. Deliberately omits connector names, temperature and token limits — those need judgement, do not drift, and copying them would make this a seventh document to keep in sync. Flags a pointer into a blocked custom step at the point someone would otherwise follow it. | `syncFlowBuildSpec()`, `checkFlowBuildSpec()` |
