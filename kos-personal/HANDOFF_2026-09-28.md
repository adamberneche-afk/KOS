### 3. No real session is ever queued for vector classification (built, needs the Classify Flow verified)

**Update (later on 2026-09-28):** decided and built. The operator chose one
per session. A whole session can't fit through the Flow (both the input and
return cells cap at 50,000 characters, and the output is roughly twice the
input), so each session is classified in parts of at most 8,000 characters
(`LOG-xxxxxxxx_VC01of03`), and Apps Script aggregates them into one
`VECTOR_MATRIX` row under `LOG-xxxxxxxx`. The result is identical to one
call over the whole session. New sessions get their parts at intake. For
the sessions already ingested, run `previewVectorClassifyBackfill()`, then
`queueVectorClassifyBackfillBatch()` (3 sessions a batch, and it waits for
each batch to drain). It reads each session back from `CuratorInput`.
`checkVectorClassifySessions()` lists sessions still waiting on a part.

**Before the backfill:** confirm the Classify Flow exists and answers. Run
`installStudioFlowFixture()`, then `checkStudioFlowLiveness()`, and check
that its step is bound to `VECTOR_CLASSIFY_SYSTEM_PROMPT` and not the RTP
Gem, for the same reason as cause 1. The original analysis follows.

Real vector weights only come from a separate `VECTOR_CLASSIFY` staging
row. The Curator must always emit `vector_weights: null`
(`CURATOR_PROMPT.md` Rule 1). **No code path creates that row for a real
session.** The only producers are `installStudioFlowFixture()`
(`12_StudioReturnHarvest.gs`) and `runStudioInputCanary()`
(`13_StudioInputBuilder.gs`). `_chunkAndQueue()` in
`2_Ingestion_Sensors.gs` queues one `SESSION_LOG` row per chunk and
nothing else. `STUDIO_INTEGRATION_SPEC.md` records this as an **"Open
integration question — not yet resolved in this repo"** (just before
"Testing the Integration"). That is why `VECTOR_MATRIX` holds only fixture
rows.

This needs a design decision before code:

- **Per chunk or per session.** Queue one `VECTOR_CLASSIFY` row per
  `SESSION_LOG` chunk, or one per consolidated session?
- **Matching `Payload_UID`.** The pair must share a `Payload_UID` at queue
  time, so both results land under one `session_uid` in `VECTOR_MATRIX`
  (see the spec).
- **Backfill.** Should the 71 sessions already processed get a
  classification row too?

**Also unverified:** the Classify Flow itself. Its only input, the fixture
row, still says `READY`, and no `VECTOR_CLASSIFY` return has ever reached
`STUDIO_RETURN`. Either the Flow isn't built, isn't triggering, or its
returns were cleared. Its prompt binding was never examined; it should be
bound to `VECTOR_CLASSIFY_SYSTEM_PROMPT`. Check it with
`checkStudioFlowLiveness()` once a real `VECTOR_CLASSIFY` row exists.

### 4. `generateDailyPrimer` fails every morning (since Sept 18) (fixed in code and pushed; confirm ERROR_LOG has no `generateDailyPrimer` rows since)

The error is "Can't remove the last paragraph in a document section."
`_clearDocBody_()` in `6_Governance.gs`, used for `KOS_LATEST_PRIMER`,
removes children starting from the **last** one. Docs refuses to remove a
body's final paragraph, so the first removal throws. The fix is to keep the
last child and remove the others from the front, then blank the one that's
left. Handle a list item as the last child too, since `asParagraph()`
throws on one. Add a test with a fake body whose last child is a
paragraph, and one whose first child is a list item. The dated
`DAILY_PRIMER_<date>` doc is created before this step, so each day's
primer may exist even though the run reports failure.

## The backlog: only after cause 1 passes

- **145 `STUDIO_TIMEOUT` and 28 `AUDIT_REJECTED` rows** are terminal, and
  none will retry by itself. All 145 timeouts are at `Retry_Count 4`.
- **The requeue helper is built:** `19_StagingRequeue.gs`. Run
  `previewStagingRequeue()` first; it changes nothing and logs, per row,
  what it would do. Then run `requeueStagingBatch()` once per batch. A
  batch tops the in-flight rows up to 10, so a second run does nothing
  until the first batch drains. It resets everything together: `Status`,
  `Retry_Count`, the Turnstile's three Script Property maps, the old
  `CuratorInput` row (without which the Flow never fires again) and the
  old `STUDIO_RETURN` rows.
- **It also restores the transcripts.** A successful harvest overwrites the
  source doc with the model output before the audit gate runs, so an
  audit-rejected row's doc no longer holds its transcript. The helper
  restores it from the `CuratorInput` row's `SourceText`. A row with model
  output in its doc and no `SourceText` is skipped as `SOURCE_LOST`; the
  preview lists any.
- **The same gap explains the "retries spent on staleness".** The audit
  gate's own retry reverted the row to `PENDING_FLOW`, but its old
  `CuratorInput` row stayed, so the input builder never built a new one,
  the Flow never fired, and the row went stale until it died.
- **Requeue in small batches.** The Sept 10-14 errors came from draining
  235 rows at once.
- **Vector data for these sessions** comes from the classification
  backfill (cause 3), which is independent of the Curator requeue. It
  reads the transcripts from `CuratorInput`, so run it before a requeue
  batch deletes and rebuilds those rows, or after that batch drains.

## Deploying

- **Command:** push kos-personal from the Windows machine with
  `tools/clasp-sync/run.ps1`:
  - `.\run.ps1 -Latest -HeadOnly -Only kos-personal` pushes the code;
  - `.\run.ps1 -Latest -Only kos-personal` also promotes the web app's
    deployments.

  **Time-driven triggers run the latest pushed code, not a deployment
  version.** So `-HeadOnly` only protects the web app and its webhook, not
  the pipeline triggers: the pipeline changes the moment you push. After
  pushing, run `reportDeployVersion` in the editor and check the marker.

  on, it stops by itself when stale.

- **Stamp the marker.** Any change to `kos-personal/*.gs` needs
