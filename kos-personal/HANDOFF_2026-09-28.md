## The four causes, in the order to fix them

### 1. Both Gemini steps in the Curator Flow are bound to the chat personas (still open)

This is the same finding as `STUDIO_REBIND_HANDOFF.md`, and the rebind has
not happened. The Sept 28 evidence:

- **Auditor step:** 95 of the 114 failed returns hold `[🛡 THE AUDITOR]:`
  prose. `harvestStudioReturns()` needs a JSON object, and marks the row
  unretryable because a retry re-parses the same stored text. Only 18 hold
  JSON.
- **Curator step:** 91 returns open with the `[🧹 THE CURATOR —
  VERIFICATION GATE]` preamble. When the audit does run, it correctly
  rejects the Curator's output:
  - all 55 `AUDIT_LOG` rows flag the preamble;
  - 51 flag `alignment_observations` missing;
  - 51 flag `vector_weights` filled with floats (the contract says
    `null`, always).

  Every one of those is `PERSONA_CURATOR_V5_1.md` behavior, not
  `CURATOR_PROMPT.md`.

**Fix:** follow `STUDIO_REBIND_HANDOFF.md` steps 1-5:

1. Run `syncFlowPrompts()` and `syncStudioFlowBuildSpec()`.
2. Bind the Curator step to the `CURATOR_SYSTEM_PROMPT` chip.
3. Bind the Auditor step to `CURATOR_AUDITOR_SYSTEM_PROMPT`, with the
   typed label and the Curator output chip.
4. Verify with `checkStudioFlowBinding()`.

The `FlowPrompts` and `FlowBuildSpec` tabs in this export already carry
the correct rows, including the Auditor's.

**Test before the backlog:** there is nothing `PENDING_FLOW` to test with.
Plant a fresh pair with `installStudioFlowFixture()`, or drop one new
session log into the inbound folder, and watch it go through. Don't requeue
anything yet.

### 2. Nothing has been staged since Sept 10

`sensor1_scanInboundSessions` staged nothing after the Sept 10 backlog. It
threw about 2,000 errors while draining that backlog (Sept 10-14):

- mostly transient "Service Documents failed" errors;
- 180 "Too many changes applied before saving document";
- 57 `DocumentApp.flush is not a function`.

The repo has fixes for the last two (`1eabd0d` for the flush call; the
save-and-reopen batching in `2_Ingestion_Sensors.gs` around line 933),
which may or may not be live.

**First question for the operator:** have new session logs gone into the
inbound folder since Sept 10?

- **If not**, intake is fine and just idle. Cause 1 is the whole story.
- **If yes**, sensor1 is skipping them silently. That's a real bug to
  chase: check the folder ID property, the file-type filter and the
  processed-marker logic. It isn't visible from this export.

### 3. No real session is ever queued for vector classification

Real vector weights only come from a separate `VECTOR_CLASSIFY` staging
row. The Curator must always emit `vector_weights: null`
(`CURATOR_PROMPT.md` Rule 1). **No code path creates that row for a real
session.** The only producers are `installStudioFlowFixture()`
(`12_StudioReturnHarvest.gs`) and `runStudioInputCanary()`
(`13_StudioInputBuilder.gs`). `_chunkAndQueue()` in
`2_Ingestion_Sensors.gs` queues one `SESSION_LOG` row per chunk and
nothing else. `STUDIO_INTEGRATION_SPEC.md` records this as an **"Open
integration question — not yet resolved in this repo"** (just before
"Testing the Integration"). That is why `VECTOR_MATRIX` holds only fixture
rows.

This needs a design decision before code:

- **Per chunk or per session.** Queue one `VECTOR_CLASSIFY` row per
  `SESSION_LOG` chunk, or one per consolidated session?
- **Matching `Payload_UID`.** The pair must share a `Payload_UID` at queue
  time, so both results land under one `session_uid` in `VECTOR_MATRIX`
  (see the spec).
- **Backfill.** Should the 71 sessions already processed get a
  classification row too?

**Also unverified:** the Classify Flow itself. Its only input, the fixture
row, still says `READY`, and no `VECTOR_CLASSIFY` return has ever reached
`STUDIO_RETURN`. Either the Flow isn't built, isn't triggering, or its
returns were cleared. Its prompt binding was never examined; it should be
bound to `VECTOR_CLASSIFY_SYSTEM_PROMPT`. Check it with
`checkStudioFlowLiveness()` once a real `VECTOR_CLASSIFY` row exists.

### 4. `generateDailyPrimer` fails every morning (since Sept 18)

The error is "Can't remove the last paragraph in a document section."
`_clearDocBody_()` in `6_Governance.gs`, used for `KOS_LATEST_PRIMER`,
removes children starting from the **last** one. Docs refuses to remove a
body's final paragraph, so the first removal throws. The fix is to keep the
last child and remove the others from the front, then blank the one that's
left. Handle a list item as the last child too, since `asParagraph()`
throws on one. Add a test with a fake body whose last child is a
paragraph, and one whose first child is a list item. The dated
`DAILY_PRIMER_<date>` doc is created before this step, so each day's
primer may exist even though the run reports failure.

## Deploying

- **Command:** push kos-personal from the Windows machine with
  `tools/clasp-sync/run.ps1`:
  - `.\run.ps1 -Latest -HeadOnly -Only kos-personal` pushes the code;
  - `.\run.ps1 -Latest -Only kos-personal` also promotes the web app's
    deployments.

  **Time-driven triggers run the latest pushed code, not a deployment
  version.** So `-HeadOnly` only protects the web app and its webhook, not
  the pipeline triggers: the pipeline changes the moment you push. After
  pushing, run `reportDeployVersion` in the editor and check the marker.
- **Copy `run.ps1` first.** The copy in `C:\Users\adam_berneche\KOS` is
  older than the checkout's: `Copy-Item
  C:\Users\adam_berneche\KOS\KOS-main\tools\clasp-sync\run.ps1
  C:\Users\adam_berneche\KOS\run.ps1 -Force`. From the current version
  on, it stops by itself when stale.
- **Check the pushed file list.** `DEPLOYMENT_GUIDE.md`'s Round 24 banner
  still applies: `clasp push` deletes anything `.claspignore` doesn't
  match, so check that its output lists every numbered file.
- **Stamp the marker.** Any change to `kos-personal/*.gs` needs
  `node tools/deploy-drift/stamp.js kos-personal` as its own commit.
  CI's drift job checks it.
