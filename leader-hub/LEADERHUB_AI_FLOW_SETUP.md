# LeaderHub AI Drafting — Setup Guide

This document defines the complete contract for LeaderHub's optional AI
features — currently three: the Brag Board's "✨ Generate" button
(`BRAG_EMAIL`), the Trip Archive's "✨ Generate Insights from Archive"
narrative (`ARCHIVE_INSIGHTS`), and the WBL Program Summary's "✨ Generate
AI Summary" button (`WBL_INSIGHTS`). It is written for setting up the
Google Workspace Flow side of the integration — the GAS side
(`EmailBridge.gs`) is already built, generic to any job `type`, and needs
no changes to add a new one.

## Why this exists

LeaderHub was originally built with a direct Gemini API integration
(`getAPIKey`/`setAPIKey`/`callAI`), later fully removed — see
`student-leader-hub.html`'s "Removed: Gemini AI infrastructure" comment.
Getting a standalone Gemini API key (Google AI Studio, billing-enabled)
wasn't available, so every "AI"-branded feature in the app today is
actually deterministic local logic with no model behind it at all.

This restores real AI drafting **without a developer API key**, using the
same architecture `kos-personal` and `cas-ccps` already use for their own
AI integrations: a **Google Workspace Flow** — a no-code automation built
in the Workspace UI — with a **"Gemini — Generate content"** connector
step. That connector runs on your Workspace account's own built-in Gemini
access, not a separate paid API key. See `kos-personal/STUDIO_INTEGRATION_SPEC.md`
for the fullest existing description of this same pattern in this repo
("Studio" there means exactly this).

## The Bifurcation Boundary

Same principle as kos-personal's Vector Router: GAS does 100% of the
deterministic work (assembling the wins list, queuing the job, returning
the jobId, polling for the result, cleaning up old rows) and is never
trusted with generation. The Flow does 100% of the generation (writing the
actual email) and never touches app state directly — it only ever reads
one job row and writes one result back. If either side tried to do the
other's job, this breaks the same way the Bifurcation Boundary document in
kos-personal warns about.

## The handshake

```
Browser              POST action=aiDraft {type, payload}   → EmailBridge.gs
EmailBridge.gs        Appends a PENDING row to AI_Queue sheet, returns jobId
Browser               Polls action=checkAiJob {jobId} every ~3s
Workspace Flow        Polls AI_Queue sheet for Status=PENDING rows
Workspace Flow        Reads Payload, calls Gemini, writes Result
Workspace Flow        Sets Status=COMPLETE (or ERROR)
Browser               Next poll sees COMPLETE, shows the draft, stops polling
EmailBridge.gs        Deletes the row once handed back — nothing to clean up later
```

**Nothing else in the app changes if you never build the Flow.** Jobs sit
`PENDING` until the 2-hour sweep in `checkAiJob_` deletes them; the client
times out after ~90 seconds of polling (see `pollAiJob_` in
`student-leader-hub.html`) and falls back to the same local, deterministic
draft the app has always produced. AI drafting is additive, not a
replacement for anything that already worked.

## Step 1 — Locate the queue sheet

The first `aiDraft` call creates a spreadsheet named **"LeaderHub AI
Queue"** in your Drive root (via `SpreadsheetApp.create()` in
`_getAiQueueSheet_()`) and stores its ID in Script Properties under
`AI_QUEUE_SHEET_ID`. You don't need to create anything by hand — just
trigger one `aiDraft` call first (e.g. click "✨ Generate" once on the
Brag Board with an Apps Script bridge URL configured), then look for that
sheet in your Drive.

**Sheet tab:** `AI_Queue`

**Column map (0-indexed):**

| Index | Column    | Description |
|---|---|---|
| 0 | Timestamp | When the job was queued |
| 1 | JobId     | UUID, generated by `queueAiJob_` |
| 2 | Type      | Job type — `BRAG_EMAIL`, `ARCHIVE_INSIGHTS`, or `WBL_INSIGHTS` |
| 3 | Payload   | JSON string — see Step 3 below for shape |
| 4 | Status    | `PENDING` → `COMPLETE` or `ERROR` |
| 5 | Result    | The Flow's generated text (empty until done) |
| 6 | Error     | Error message, only set on `ERROR` |

## Step 2 — Build the Flow

Because every job type shares one queue sheet and one generic GAS
dispatch, the simplest setup is **one Flow per job type**, each watching
the same sheet but filtered to its own `Type` value. In Google Workspace,
create a new Flow (or AppSheet Automation / whichever Gemini-connected
no-code automation product your Workspace edition exposes — the connector
names below are what to look for regardless of the exact product name)
for each row of the table below:

| # | Connector | Configuration |
|---|---|---|
| T | Google Sheets — Row updated | Spreadsheet: the "LeaderHub AI Queue" file from Step 1 · Tab: `AI_Queue` · Condition: `Status = PENDING` AND `Type = <job type>` |
| 1 | Gemini — Generate content | System prompt: full text of the job type's prompt file, pasted verbatim · Input: `@trigger.Payload` (the JSON string in column 3) · Output format: plain text only, no markdown, no preamble |
| 2 | Google Sheets — Update row | Row: `@trigger.row` · Result column (6): `@step1.geminiOutput` · Status column (5): `COMPLETE` |

| Job type | Prompt file | Trigger `<job type>` |
|---|---|---|
| Brag Board email | `BRAG_EMAIL_FLOW_PROMPT.md` | `BRAG_EMAIL` |
| Archive Insights narrative | `ARCHIVE_INSIGHTS_FLOW_PROMPT.md` | `ARCHIVE_INSIGHTS` |
| WBL Program Summary | `WBL_INSIGHTS_FLOW_PROMPT.md` | `WBL_INSIGHTS` |

Each Flow is independent — build one, test it, then build the other
whenever you're ready. Neither blocks the other: a row with a `Type` no
Flow is watching for just sits `PENDING` until the 2-hour sweep in
`checkAiJob_` removes it, and the client falls back to whatever
deterministic result that feature already produces on its own.

**On failure** (step 1 errors, or produces something clearly wrong):
update the row's Status to `ERROR` and Error column with a short message
instead. Do not leave the row at `PENDING` forever — the client is
actively polling and will otherwise wait out its own timeout with nothing
to show for it.

**Polling interval:** every 1 minute is plenty — this is a single-user,
on-demand feature, not a high-volume pipeline. The client polls every ~3
seconds for up to ~90 seconds waiting for the Flow to notice and finish,
so a 1-minute Flow poll interval means most requests land in one or two
client poll cycles after the Flow actually picks the row up.

## Step 3 — Payload shape (what the Flow reads)

`queueAiJob_`'s Payload column contains a different JSON shape depending
on `Type`.

**`BRAG_EMAIL`:**

```json
{
  "audience": "green",
  "audienceLabel": "Ms. Green",
  "tone": "professional supervisor update with DSP evidence framing — reference Standard 1 (Instructional Planning) and Standard 2 (Professionalism/CTSO) where applicable. Be specific and evidence-oriented.",
  "weekLabel": "August 11",
  "sections": [
    "DECA results:\n• Jane Doe — International Business: 1st place",
    "Field trips:\n• Fall DECA Conference"
  ]
}
```

`sections` is the same bulleted-section text the deterministic fallback
draft already assembles (see `_generateBragEmailInner()` in
`student-leader-hub.html`) — the Flow's only job is turning that raw list
into a well-written email in the given `tone`, not re-deriving what
happened this week. `tone` comes straight from `BRAG_AUDIENCE[audience].tone`
in the client — four audience presets (Ms. Green, Admin, DECA Parents,
Personal Log) each with their own tone description.

**`ARCHIVE_INSIGHTS`:**

```json
{
  "totalTrips": 6,
  "totalStudents": 214,
  "avgCostPerStudent": 38,
  "tripTypes": [
    { "type": "overnight", "count": 2 },
    { "type": "same-day", "count": 4 }
  ],
  "glows": [
    "Fall DECA Conference: Students self-organized the vendor floor visit schedule with no adult prompting."
  ],
  "grows": [
    "Spring Career Fair: Bus arrival timing needs a 15-minute buffer next time."
  ]
}
```

The `totalTrips`/`totalStudents`/`avgCostPerStudent`/`tripTypes` fields
are the exact same numbers already rendered as a stats grid on-screen
(see `generateAIInsights()` in `student-leader-hub.html`) — that
arithmetic is computed locally and never re-derived by the Flow. The
Flow's only job is finding a real pattern across `glows`/`grows` and
writing 2–4 sentences of prose about it, using the stats only as
supporting context — see `ARCHIVE_INSIGHTS_FLOW_PROMPT.md`'s rules against
just restating the numbers or inventing a pattern that isn't there.
Queued only when the archive has at least one glow or grow recorded —
see `generateAIInsights()`'s guard before it calls `aiDraft`.

**`WBL_INSIGHTS`:**

```json
{
  "totalStudents": 12,
  "onTrack": 8,
  "notStarted": 1,
  "sbeDone": 6,
  "sbeTotal": 10,
  "avgHours": "22.4",
  "totalHours": "269.0",
  "attentionDetails": [
    "1234567@ccpsnet.net: 18 of 30 required hours logged; no reflections logged yet"
  ],
  "sbeNotes": [
    "Location for SBE Operation: Waiting on facilities for a confirmed cart storage spot."
  ]
}
```

Same split as `ARCHIVE_INSIGHTS`: the summary numbers are the exact
numbers already rendered in the WBL Program Summary modal (see
`wblAIInsights()` in `student-leader-hub.html`), computed locally and
never re-derived by the Flow. `attentionDetails` is built by
`_wblAttentionReason()` — one line per student flagged `needs-attention`
or `not-started`, with the specific reason(s) (missing agreement, hours
short of the 30 required, no reflections logged), not just a pass/fail
badge. `sbeNotes` is the free-text notes field on any incomplete SBE
checklist item that has one. The Flow's only job is finding a real
pattern across those two lists and writing 2–4 sentences about it — see
`WBL_INSIGHTS_FLOW_PROMPT.md`'s rules against restating the numbers or
inventing a pattern that isn't there. Queued only when there's at least
one attention item or SBE note to summarize — see the guard at the top of
`_wblGenerateNarrative()`.

## What data this sends through Gemini

By default, all three features send free-text content **as-is**, which
may include real student names (e.g. a DECA placement in a Brag Board
win, a student named in a trip's glow/grow reflection, or a student named
in a WBL attention item). That's a deliberate choice, not an oversight:
LeaderHub is Adam's personal professional-communications tool, not a
student-education-record system.

**Optional roster-based substitution.** Settings → "Student ID Lookup —
AI Privacy" lets you upload a CSV roster (any header naming a name column
— `Name`, `Student`, or `First`/`Last` — and an ID/email/login column).
When a roster is uploaded, **all three** AI features swap every matched
student's name for their CCPS ID in the form `{7-digit ID}@ccpsnet.net`
**before that content ever leaves the browser** — the request Gemini
actually sees never contains the real name. The response comes back with
those same ID strings, which the browser then swaps back to the real name
before showing you the result — so what you read still reads naturally,
only the network payload in between was substituted. This is client-side
text substitution (`_substituteNamesForIds`/`_restoreNamesFromIds` in
`student-leader-hub.html`, called from `_generateBragEmailInner()`,
`generateAIInsights()`, and `_wblGenerateNarrative()`), not a schema field
or a server-side feature — no student ID is ever stored anywhere but this
browser's `localStorage`, same as everything else in LeaderHub.

Substitution is **fail-open**, not fail-closed: any name not found in the
uploaded roster (typos, students not yet added, non-student names) is
sent through unchanged. There's no attempt to heuristically detect and
redact unrecognized names — a general-purpose name detector on free text
would be unreliable and could just as easily mangle a legitimate sentence
as protect a real one. The Settings panel says this plainly so it's never
an assumed guarantee. If a specific audience shouldn't see a real name at
all — mapped or not — edit the generated draft before sending; nothing
here auto-sends anything, every path ends in an editable textarea.

See each job type's prompt file "Placeholder rule" (`BRAG_EMAIL_FLOW_PROMPT.md`,
`ARCHIVE_INSIGHTS_FLOW_PROMPT.md`, `WBL_INSIGHTS_FLOW_PROMPT.md`) for the
corresponding instruction that keeps that Flow's Gemini step from
reformatting those `{id}@ccpsnet.net` strings — the reverse-substitution
above only works if the exact string comes back unchanged.

## Testing the integration

All three job types follow the same handshake, so the same test procedure
applies to each — just swap the feature and status element referenced.

1. Configure an Apps Script bridge URL in LeaderHub Settings if you
   haven't already (existing `EmailBridge.gs` setup, unchanged).
2. **Brag Board:** open Brag Board, pick a week with at least one win,
   click "✨ Generate". **Archive Insights:** open Trip Archive → "📊
   Archive Insights" → "✨ Generate Insights from Archive" on an archive
   with at least one glow or grow recorded. **WBL Program Summary:** open
   WBL Tracker → "📊 Program Summary" → "✨ Generate AI Summary" on a
   program with at least one student flagged or one SBE note recorded.
3. The feature's status line should show a polling message
   (`brag-ai-status`: "⏳ Drafting with AI…" / `archive-ai-status` /
   `wbl-ai-status`: "⏳ Drafting narrative/summary with AI…"). Confirm a
   new row appears in the "LeaderHub AI Queue" sheet's `AI_Queue` tab with
   `Status = PENDING` and the expected `Type` (`BRAG_EMAIL`,
   `ARCHIVE_INSIGHTS`, or `WBL_INSIGHTS`).
4. Manually set that row's Status to `COMPLETE` and Result to any test
   string, to confirm the client picks it up correctly without waiting on
   a real Flow build.
5. Once the real Flow is built (one Flow per job type, per Step 2 above),
   repeat step 2 and confirm the Flow claims the row, writes real output,
   and the client shows it within the polling window.

**Minimum valid test row (columns 5–6 for a manual COMPLETE test):**
`COMPLETE` | `Test draft — everything is wired correctly.`
