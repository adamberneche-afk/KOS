# Agent notes

The traps and conventions that earlier agent sessions hit and that still
hold. They come from the "notes for the next agent" in the archived session
handoffs (2026-10-05 to 2026-11-08) and the 2026-11-21 structure audit. One
note per point, each ending with the handoff date(s) it came from. The
handoffs keep the original notes word for word: [`archive/INDEX.md`](../archive/INDEX.md)
lists them, and `node tools/archive/search.js --kind handoff <text>`
searches them. The newest handoff (`meta/HANDOFF_<date>.md`) adds its own
notes. Where the code or the newest handoff disagrees with a note here,
they win. [`CLAUDE.md`](../CLAUDE.md) holds the working agreements and the
debt rules; this file doesn't repeat them.

## Working with the operator and the repo

- **Name the project and the file** for every function you ask the operator to run (for example `buildWarmUpQueues()`, Central Ledger, `24_WarmUpBridge.js`). Several files are in more than one project, so say which copy. (10-18, 10-19)
- **The editor's Run menu hides functions whose names end in `_`.** An entry point the operator runs needs a public name. Don't add a `_` to hide an editor function from web-app callers, because the Run menu then hides it too. (10-18, 10-31)
- **A function that opens a prompt or dialog** (it calls `getUi()`, like `setCurrentTerm()` in the Central Ledger's `10_AdminRecoveryPanel.js`) fails from the editor. Tell the operator to run it from the sheet's menu. (10-20)
- **A check that reads fixture rows needs them planted first.** Give the operator both steps, for example leader-hub's `installAiFlowFixtures()` before `checkAiFlowFixtures`. (11-01)
- **After a manifest scope change** to a web app that runs as the deploying admin, the admin runs a function from the editor and approves the new scope, then tests one submit before a class depends on it. A blocked consent prompt points to the district's Admin console API controls. (10-17)
- **Check CI on the PR's head commit before merging**, every time. (10-22)
- **Stacked PRs with squash merges:** after the lower PR merges, rebase the upper one with `git rebase --onto origin/main <lower branch>`, retarget its base to main, and push with `--force-with-lease` (your own branches only). Check that it builds before pushing. CodeQL runs only on a PR whose base is main. (10-28, 11-08)
- **Parallel agents** work in `git worktree`s off `origin/main`. PRs that touch 07, 13 or the READMEs usually need a rebase after the first one merges. Cherry-pick a helper agent's commit onto the session branch and run the tests there. Main also gets the hub's `chore: log … decision` commits. (10-22, 11-08)
- **Commit IDs from before 2026-10-31 are gone** because history was rewritten that day. Cite PR numbers instead. (10-31)
- **Ideas for later go in [`BACKLOG.md`](./BACKLOG.md)**, one line each, not in a handoff's queue. Each handoff moves the plan's "The next 14 days" window forward. (10-17, 10-18)
- **The decision register** (`DECISION_REGISTER`) can repeat a decision when a later log echoes it. Resolve the original and mark each repeat `DROPPED` with "Duplicate of <id>". Echoes found at intake go to `DECISION_ECHOES`. (11-08)
- **SMPs live in `SMP_REGISTER`** (BRAIN_TRUST_INDEX) and `01.3_SMP_PROPOSALS`, never in the repo ([`SMP_PROCESS.md`](./SMP_PROCESS.md)). Cite an SMP by its register number; a session never numbers one. SMP-018 limits what the KOS Project may write, and a change to that list needs its own SMP. (10-12)

## Deploying

- **The push is `node run.js`** (`tools/clasp-sync/`). It stamps each build's deploy marker with the GitHub zip's commit, so there is nothing to stamp or commit by hand ([`tools/deploy-drift/README.md`](../tools/deploy-drift/README.md), "run.js stamps the push"). `--verify` checks the live deployments. `--latest` pushes every project without asking, but stops when its own copy differs from the checkout's and prints the `copy /Y` line to fix it. (10-29, 11-01)
- **The operator's registry folder** (`clasp-registry\`, outside the repo) holds script IDs, `deployments.txt` and the Project's doc links (`kos-project-links.txt`, `NAME=https://...`), never the repo. A `deployments.txt` line is the deployment ID alone: a pasted ` @n` makes `run.js` report the live deployment as "not in deployments.txt" and move nothing. `PROJECT_INSTRUCTIONS.md` keeps `<link to NAME>` placeholders that `node run.js --instructions` fills, so tell the operator when you add a placeholder. (10-12, 10-18, 11-01)
- **central-ledger is also a library.** `unified-manual` pins it at a fixed version in `cas-ccps/clasp/manifests/unified-manual.appsscript.json`, so a push doesn't reach the setup wizard's library calls (`importCompetencyRegistry()` in 22b, `importPacingGuide()` in 31, `importCompetencyRubrics()` in 32). If one of those changes, the operator cuts a new library version and the PR bumps the pin. (10-12)

## Checks, docs and generated files

- **Generated files are never hand-edited.** Run the generator; its `--check` (in CI or a test) fails while a committed copy is stale. [`tools/README.md`](../tools/README.md) lists them: lesson data, rubrics, cartridges, flow prompts, the guides' notebook copies, the setup guide reference. The codebase-notebook output isn't committed at all. (10-05, 10-06, 10-23, 11-01, 11-08)
- **The setup guide's reference is generated.** A change to a cas-ccps file list, Script Property, trigger or flow needs `node tools/setup-guide/build.js`. Two PRs can each pass and still leave main stale, so regenerate after the second one merges. (11-08)
- **Write a function with parentheses in a doc only if it exists.** doc-currency fails a doc that names a missing one (`documented-function-missing`), plans included. Describe a planned function in words. (10-10, 10-12, 10-27)
- **doc-currency checks Markdown only.** It reads `.html` for declarations, not facts, so an HTML guide is checked by hand. It skips a whole file when a "superseded"-style word (its `supersededMarkers`) is in the first `bannerScanLines` lines, which can hide a stale mention. (10-23)
- **doc-currency reads `.html` as JavaScript** to find declarations, so an apostrophe in page text can hide a later declaration. If a declared function is reported missing, look for one. It walks the whole working tree, so move helper agents' worktrees (`.claude/worktrees/`) aside to see only real findings. (10-22)
- **The release check gates CI** (`tools/release-check`). Don't commit Drive IDs, Docs links or web-app URLs, fixtures included; build a made-up one at run time (as `ledger-schema-guard.test.js` does). (11-08)
- **CodeQL reviews each PR.** Escape `\` first in any escaping code. In tests, it flags a substring check on a host (`a.includes('evil.com')`) and a one-pass tag strip: use `assert.doesNotMatch`, or `split(/<[^>]+>/).join('')`. (10-23, 11-08)

## Apps Script, the sandbox and tests

- **A test sandbox loads every file its code reaches.** gas-lint's `sandbox-scope-gap` names each missing file, and `typeof-guard-same-project` refuses a `typeof fn === "function"` guard for a function the project always has, so load the file instead ([`FLOW_DOCTRINE.md`](./FLOW_DOCTRINE.md) rule 12). A test that drives a whole project takes its file list from `tools/gas-lint/project-map.json`. Adding a call to another file usually means adding that file to several sandboxes. (10-08, 10-10, 10-18, 10-21, 10-23, 10-28, 11-01)
- **Which projects hold a shared file is in `project-map.json`.** For example, `63_DocHeader.js` is in the Central Ledger and the Student Dashboard only, while 55b and 68 are in the Central Ledger and the Teacher Dashboard, not the Student Dashboard. A lesson change goes live on the dashboard with the Teacher Dashboard push. (10-18, 10-22, 10-28)
- **00 is split by project.** Code only one project uses is in `00c_CentralLedgerShared.js`, `00d_TeacherDashboardShared.js` or `00e_StudentDashboardShared.js`. A sandbox that loads `00_SharedConfig.js` by hand loads all three after it. One that takes a project's files from `project-map.json` already has its own, so don't add it twice (a duplicate `const` throws). (11-21)
- **00 can't call `DocumentApp`**, because every project loads 00 and gas-lint wants the Docs scope wherever it appears. A Docs reader lives in a project's own file, which is why the context-week readers are twinned (07's `_tdContextWeeks_`, 13's `_dashContextWeeks_`). (10-27)
- **A function called per row must not call `getConfig_()`**, which reads every Script Property. Memoize it per execution (29's `_studentIdPattern_`, 02's `_intakeMemo_`). (10-29)
- **A run-overlap guard is `claimRunSlot_(key, ms)`** (00c), never a plain check-then-set on a Script Property. A read-modify-write of `_CONFIG` reads `freshConfigValues_()` (00d) under the script lock. (10-31)
- **A Drive sweep stopped by its time budget** must skip what it already handled, so that the next run finishes the job (kos-personal 6's `SWEEP_TIME_BUDGET_MS`). gas-lint's bounded-loop check requires the cap. (10-23)
- **Dates across vm contexts:** a Date made in a test fails `instanceof Date` inside the GAS sandbox. Code that a test feeds dates to uses `Object.prototype.toString.call(v) === "[object Date]"`. (10-27)
- **The harness hands a test a copy of a constant.** To change one (say `LESSON_ASSIGNMENTS`), load a small script after it, as `video-links.test.js` does. 55b and `cas-ccps/data/CompetencyRubrics.json` load in the sandbox, so a test can check every real lesson. (10-22, 10-24)
- **Tests that need git history build their own repo**, since CI's checkout is shallow (`deploy-drift-check.test.js`'s `commitContains` test). (10-29)

## The dashboards' pages

- **The pages are `.html` files** (`07_TeacherDashboardPage.html`, `07_MyContextPage.html`, `13_StudentDashboardPage.html`): plain HTML and JavaScript with no template-literal escaping. A server value is `<?!= name ?>`, set in the build function's `renderPageTemplate_("<page>", { name: ... })` call. Add both, or `dashboard-pages.test.js` fails, because Apps Script throws on an unset name. (11-21)
- **A test reads a page's text from the `.html`**, and the sandbox's `HtmlService` renders it. To run client code, build the page (`buildDashboardHtml_`, `buildStudentDashboardHtml_`) and run its scripts in a vm. Examples are `teacher-dashboard-inline-js.test.js`'s `firstContextWith` (replace `context.document` with a plain object, since a proxy ignores assignment) and `student-dashboard-warmups.test.js`'s `page()`. (10-22, 10-24, 11-21)
- **Render a page to check a UI change:** build it through the sandbox, stub `google.script.run` with fixture data, and screenshot it with Playwright (`/opt/pw-browsers`). (10-22, 10-27)
- **The Teacher Dashboard's modals open with the class `open`**, not `show` (a test pins it). Link text is `#1557b0`; `dashboard-plain-words.test.js` rejects `#1a73e8` as a text colour. (10-22, 10-24)
- **Student Dashboard client calls go through the page's `scriptRun()`**, never `google.script.run` directly, so demo mode answers from its stubs. (11-08)
- **Nothing is stored in the browser** in cas-ccps or kos-personal (`tests/tools/no-browser-storage.test.js`). Drafts and conveniences live in page memory. (10-22)
- **Words come from one place.** 00 holds the terms (`CAS_*_TERMS`), `CLIENT_WORDS_JS` and `termLabel_`; 13's `resolveStudentStatus_`, the Teacher Dashboard page's `BADGE_WORDS` and 07's `_tdFlagReason_` name each stage. A new surface reuses them. (10-22)
- **Settings:** a new switch goes in 00c's `DASHBOARD_SETTING_KEYS`, 07's `TD_SETTINGS` and `SHARED_CONFIG_KEYS`, and is read with `pivotFlagFor_()`. `saveSettings` writes the `_CONFIG` row and a `SettingsLog` row. (10-27)
- **A public function in a web app needs a caller check.** In the Teacher Dashboard, Student Dashboard and leader-hub projects, any top-level function without a trailing `_` can be called by any visitor and runs as the owner. Call `_isAuthorizedTeacher_`, `requireScriptOwner_` (00b, which lets triggers through) or `_lhRequireOwner_` first, or list the function with a reason in `tools/gas-lint/webapp-public-allow.json`. (10-31)

## cas-ccps: data, sheets and config

- **Sheets turns ID-like text into dates** ("8175-1"). Write such cells with number format `@`, and read them through the existing text helpers (`competencyIdText_`, `_lessonPeriodText_`, `_normalizeLessonDateCell_`). (10-07, 10-08)
- **A Studio flow writes its timestamps as text.** Read them with `sheetTimestampMs_` (00), never `new Date(...)`. A formula comparing such a column with `NOW()` matches every row, and `COUNTIFS` with a date criterion matches none. (10-20, 10-22)
- **The queue's lesson dates are `YYYY-MM-DD` text.** `new Date("2026-10-21")` is midnight UTC, the evening before in New York; use `wfbNormalizeDateIso_` or compare the strings. (10-20)
- **A Ledger row's ConfigID is the student's workspace ID** (`VDOE-…`), not the assignment's, and names no course. Get the course with `ledgerRowCourseCode_` (00), and read a student's TeacherMatrix rows through `readStudentAssignments_` (54) first. (10-21, 10-22)
- **TeacherMatrix's competency IDs are the four `Milestone{1-4}CompetencyId` columns**, comma-separated. Find them by header (`s33CompetencyColumns_`, 33). 33 and 53 find the matrix the same way: `MatrixRegistry`, then `TEACHER_MATRIX_SS_ID`. (10-20, 10-21)
- **WarmUpQueue's columns are 00's `WQ` and `WQ_HEADERS`.** 24 writes the first `WQ_BASE_WIDTH` (21). `archive_status`, `delivered_at` and `answered_at` (21 to 23) fill in on first use, and a new column goes after them, in both. (10-10, 10-23)
- **SCRDecisionLog has three writers that append a whole row by hand** (07 twice, 00d). Change all three together. (10-10)
- **Evidence and states:** SCR counts one piece per assignment at its best (30's `aggregateEvidence_`). The Teacher Dashboard's states come from Ledger columns written by `recordEvaluationResult_` (37). SCR scale: 1 is the highest and 1–3 is satisfactory (`SCR_COMPLETED_MAX_RATING`). Rows submitted before #186 have a blank `SubmissionTS`. (10-08, 10-12, 10-18, 10-27)
- **Ledger status `SCHEDULED`** is a doc the rollout made ahead and hasn't shared: no Student Dashboard card, submit refused (`NOT_OPEN_YET`), archived like ACTIVE. Only `58_LessonRollout.js` sets it ACTIVE. A rollout that stops short schedules `runLessonRolloutCatchUp`; its Script Properties are `ROLLOUT_CATCHUP` and `ROLLOUT_BUSY_UNTIL`. (10-18, 10-29)
- **`ERROR_EVALUATION`** is a staging, queue and Ledger status. 37 sets it on a result it can't use, 03 closes and reports it, 34's watchdog counts it as a terminal failure, and a resubmission builds a fresh FlowInput row. (10-22)
- **Shared switches** (`FEEDBACK_AS_COMMENT`, `ROLLOUT_AUTO_APPLY`, `WARMUP_TEXT_BOX`, the `PIVOT_*` flags) live in `SHARED_CONFIG_KEYS` and are read with `pivotFlagFor_()`. A value is `off`, `all`, a course code or a list ("8175,8177", read by `_pivotValueOn_`), and a course-wide action needs "all". A Script Property overrides the Ledger's `_CONFIG` tab in its project. Other projects see a `_CONFIG` change within 10 minutes, or at once after `refreshSharedConfig()`. (10-10, 10-12, 10-18, 10-27)
- **Terms:** `currentTerm_()` (00) is the term (`2627_MP1`, rolled over by `MARKING_PERIOD_ENDS`); never read `CURRENT_TERM` directly. Visibility, archiving and enrollment go by school year (`_schoolYearOfTerm_`, `sameSchoolYearTerm_`), never the exact term. (10-12, 10-19)
- **Retention periods are Script Properties.** `_retentionCutoff_()` (00) counts whole school years with an August start. (10-17)
- **The Central Ledger needs `TEACHER_EMAIL` and `TEACHER_NAME` as Script Properties.** The warm-up queue builder (24) matches ClassSchedule rows on the email, and every warm-up snapshot carries the name. (10-18)
- **`ClassSchedule` day types:** `DAILY`, `DAILY_HALF` (a new warm-up on the first day of each pair), `ODD` and `EVEN` (the date's parity). A period label is text (`3-Odd`), never a number. `NOT_MEETING` in WarmUpQueue is a warm-up queued for a day its period didn't meet. A typed `FALSE` in an active column (`ClassSchedule`, `CanvasSectionMap`) is inactive, so read the cell as a boolean or as text. (10-18, 10-19)
- **A student's period can come from `PeriodOverride`** (52) before `CanvasSectionMap`: enrollment, the rollout and the relabel read it. The tab holds accounts, so it's in the FERPA data map, and it is cleared at year end. (10-21)
- **The course rule:** new code has no course number, course name or lesson format in it; read the course from data. The existing rules (00's `warmUpCourseCode_`, 24's `courseCodeFromName_`, 51's `_cybCourseCode_`) are the ones to replace. (10-22)
- **The bell schedule:** a day's schedule is 00's `bellScheduleFor_(ymd, overrides)`. Without `overrides` it reads ⚙ Settings' `SCHEDULE_DAYS` once per run, so pass `{}` in a test that must not read config. The school's schedules come from `BELL_SCHEDULE` (defaults in 00); leader-hub keeps its own copy. (10-27, 10-28)

## cas-ccps: jobs, flows and docs

- **The Ledger's frequent jobs run in `runLedgerCycle` (64).** Don't add a 1-, 5- or 10-minute trigger for a Ledger job: add it to `LC_JOBS`, and let its installer (`installLedgerCycle()`, `installQueueWatchdogTrigger()`) enable it in the cycle. A job's failure shows in the `[LC] Errors:` log line. A trigger belongs in the project that defines its function; the Unified Manual installs no Central Ledger trigger. (10-17, 10-18, 10-19, 10-21)
- **Studio drops runs when many rows change at once** ("Couldn't access the spreadsheet"). Write Studio input rows paced (`WFB_INPUTS_PER_RUN`, 41). Flow 2's starter fires on an edit, not on an appended row, so `buildFlowInputRows` (37) appends the row and then sets ReadyStatus as its own edit. Flow 3's inputs do start on appended rows; don't assume the same for a new flow. (10-18, 10-19)
- **Flow prompts start in the spec.** Edit `cas-ccps/docs/CAS_Flow3_Flow4_Specification.html`, run `node tools/cas-ccps/generate-flow-prompts.js` to write 40, and never edit `40_FlowPrompts.js` by hand. A new key also goes in `FLOW_PROMPT_KEYS`. After the push the operator runs `syncFlowPromptsToSheet()`. Studio's Ask Gemini steps read the PromptText chip, so a prompt change goes live with the push; they must list no Drive sources. (10-22, 10-24, 11-01)
- **Each flow has its own plausibility check** in 41: `wfbFlow3Plausible_` (against `WFB_FLOW3_SOURCE_FIELDS`), `wfbFlow4Plausible_`, and `_wfbCheckPlausible_` for Flow 3's lead-in. A failure reason names a count, never the student's words. (10-21, 10-22)
- **Flow 3 output passes a shape gate**, `wfbWarmUpShapeProblem_(text, anchor)` (41). It never delivers model text that carries the prompt's wording, a competency code or a list, and the teacher's `warmup_anchor` is the fallback. Check the overnight fallback count before trusting a Studio prompt change. (10-18, 10-22)
- **Text-box warm-ups have no doc.** Code that reads a warm-up's prompt or answer must handle both the doc (`evaluateWarmUpDoc_`) and the `WarmUpTextBox` row (`evaluateWarmUpText_`, 25): check `WQ.DOC_ID` before trusting a doc path. Student writing in that row is FERPA data. (10-18, 10-20)
- **Warm-up seeds and scoring:** `WarmUpPlan` (55) picks a day's seed, and `getWarmUpAnchor_` (31) takes it before the current lesson. With no plan row, the seed is a lesson already started, the same for both days of a pair (`reviewWarmUpKey_`, 55). The nightly run scores what 25's `_selectWarmUpsToScore_` picks, and `previewMissedWarmUpScoring()` runs the same selection read-only. Baseline warm-ups are decided by 41's `wfbBaselineState_` and `wfbBaselineChoice_`. (10-18, 10-19, 10-24)
- **The warm-up window has one rule:** only the current warm-up (on its day) and the last one (until the end of the next class day) are open. 13's `_dashWarmUpPair_` decides it, and 25's `_answeredLate_` handles a late answer. (10-24)
- **The overnight check (`34c_OvernightHealth.js`)** writes LAST NIGHT in the CAS signal on every watchdog run and emails it once a day (`CAS_OVERNIGHT_MAILED`). It reports counts only. Its "last 24 hours" counts by when a return was harvested, not the lesson day, so group by the queue row's lesson date before drawing conclusions. (10-18, 10-20)
- **The CAS attention signal** (`34b_CasAttentionSignal.js`) is written at the end of every `runQueueWatchdog()`, with counts only and students first. Its data boundary is in `cas-ccps/docs/FERPA_DATA_MAP.md`, and adding anything but counts is the teacher's call. (10-12)
- **The response zone ends at `[CONFIG_ID:`.** Don't move or rename it: 01, 03, 13 and Flow 2's extract step stop there. Never put the full response marker line (`── YOUR RESPONSE BEGINS HERE ──`) in text that can appear above the zone, because every extractor takes the first match. The doc markers' text (63) is never reworded. (10-17, 10-18, 10-24)
- **The assignment in a doc is a table** (02's `_docAssignmentTable_`). Body `getText()` includes it, but code that walks body children must allow a `TABLE`. (10-24)
- **Evaluations go in the feedback zone** (`_fiInsertEvaluation_`, 37), or into a Drive comment when `FEEDBACK_AS_COMMENT` is on. Code that needs the result reads the Ledger (`recordEvaluationResult_`), never the doc text. (10-08, 10-17, 10-18)
- **Reflection questions come from code** (00e's `REFLECTION_FRAMES`, `chooseReflectionQuestions_`), never a model. Submit chooses them again and checks the answers against them. (10-24)
- **The student's record** (13's `getMyCompetencies`, `getMyWarmUpHistory`, `getMyContext`) takes the identity from the session only, never from a parameter. `SCRSuggestions` never reaches a student. (10-27)
- **CAS mail goes through `casMail_` (00)**, and a share with the teacher goes through `shareWithoutEmail_` (02) so it sends no email. (11-08)
- **The turn-in switch** `TURN_IN_CODE_COURSES` takes course codes and lesson IDs. One function reads it: `turnInSwitchCovers_` (71). (11-08)
- **Student words that reach a prompt** go through `findSystemText_` (refused at the student's save) or `neutralizeSystemText_` (00, at prompt build). A new machine marker goes on `SYSTEM_TEXT_PATTERNS` in the same commit. (10-10, 10-31)
- **The family signal** (`60_FamilyMailSentinel.js`, set up in `cas-ccps/docs/FAMILY_MAIL_SENTINEL.md`) reaches the KOS Project only as the name-free `KOS_FAMILY_SIGNAL` doc, never the mail. Don't widen what it carries without the teacher's say. `_fmsNeedsReply_` decides between its two tiers, and system senders (`FMS_SYSTEM_SENDERS`) never reach the log. The triage prompt's one source is `cas-ccps/prompts/FAMILY_MAIL_TRIAGE_PROMPT.md`; regenerate 61 with `node tools/cas-ccps/generate-family-mail-prompt.js`. (10-12, 10-21)

## cas-ccps: lessons and curriculum

- **The student side of a lesson is its prompt file**, `cas-ccps/curriculum/lessons/<course>/prompts/<lesson>.md`, used only when it says `status: approved`, in both courses. Its first line is "Assignment:" (or "Project:", "Discussion:", "Extra Credit:"), which the doc and the cartridge drop. (10-10, 10-12, 10-28)
- **After a lesson change,** run `node tools/cas-ccps/build-lesson-assignments.js` and `node tools/cas-ccps/build-canvas-cartridge.js`, then tell the operator to push, run `refreshAssignments()` (53) and re-import the cartridge. Canvas text otherwise changes by hand, never by re-import. `seedAssignments()` never rewrites a matrix row; `refreshAssignments()` brings existing rows up to the repo and rewrites a LIVE row's prompt doc. (10-10, 10-12, 10-19, 10-24, 11-01, 11-08)
- **Competency lines** cite the 2025 task number with the state's wording from `cas-ccps/data/CompetencyRubrics.json`. A mismatch lands in `cas-ccps/curriculum/lessons/COMPETENCY_REVIEW.md` with no ID. `COMPETENCY_TIERS.json` must cover exactly the lesson's competency lines, one tier each (the builder throws otherwise). The two `COMPETENCY_TRACKER.md` files are built from the lessons' alignment sections. (10-10, 10-12, 10-19, 10-21)
- **One home each:** objectives in `curriculum/lessons/STUDENT_CRITERIA.json` (first person, "I can …", which 53 writes to the TeacherMatrix's `StudentObjectives`), and video links in `curriculum/lessons/VIDEO_LINKS.json`. A new lesson or a changed tier needs its objectives. (10-24)
- **Canvas drops a task's closing "Submission:" part**, so anything students must see goes before it. The Definition of Done carries THE TASK, the tiers and a PASSING RULE line, which the harvest reads. (10-19)
- **Lessons in parts:** `PARTS.json` is live, while `PARTS_DRAFTS.json` waits for approval and the builder never reads it. `node tools/cas-ccps/check-parts-drafts.js [file]` checks a split, and `render-parts-drafts.js` regenerates `LESSON_PARTS.md`. A part's paragraph must start with "Part n:" after a blank line. 13 reads a part from StudentAssignments (the `-P<n>` ConfigID). (10-28)
- **Work files by type:** a part's `workType` (`doc`, `form`, `slides`, `sheet`) must match its planned `workFile`, and its checks (`formChecks`, `slideChecks`, `sheetChecks`) are exact. `FormSnapshots` holds every non-doc copy's snapshot whatever the type. Marking a part needs a blank template in the operator's Drive, `WORK_TEMPLATE_<PART KEY>`, a `PARTS.json` edit, the generators and `render-parts-drafts.js`. Template file IDs never go in the repo. (11-08)
- **Lesson drafts:** `LessonDrafts` statuses are exact strings (`MERGED`; the PR goes in `pr_url`). `import-lesson-drafts.js` runs 65's own `_ldCheck_` in a vm, so the dashboard and the import can't disagree. 65 compares the task without the builder's "What your work needs to show" checklist (`_ldTaskText_`). (10-22)
- **The lesson `.md` files mirror the teacher's Drive docs** (their header names the doc by title), so a change in one should reach the other. Edit a Drive doc in place with the Google Docs connector: check it against the repo's text first, change only the edited lines, and verify afterwards. Insert new text before deleting old so it keeps the doc's font, and anchor new list items on a list paragraph. (10-10, 10-12, 10-24)

## kos-personal and the KOS Project

- **A session with no Vector State row:** run `explainUnclassifiedSessions()` (20) first, which names the state and the call. Nothing requeues from STAGING_ARCHIVE; `resetUnrebuildableRows` (21), given a session's full UID, re-queues it from CuratorInput text. (10-23)
- **Studio prompts for the Curator, Vector Classify and Curator Auditor flows** come from the `FlowPrompts` tab (16), filtered on `PromptName`. Check that a flow exists before asking the operator to paste a prompt into it. (10-21)
- **Gemini, as tested 10-05:** an app runs only from a chip the operator types in the message (pasted `@Name` text and chips in the Instructions call nothing), mail goes through `@Workspace`, and notebook retrieval matches a source's text, not its title. That's why each notebook source carries a `Notebook source: {NAME}.` line. (10-06)

## leader-hub

- **LeaderHub runs only served.** Its data comes in `window.__LH_BOOT__` (`lhBootData_`, Data.gs), and saves go through `google.script.run`. A new `lh_*` key needs a server home (`LH_CONFIG_KEYS` in Config.gs, `LH_DATA_TABS` in Data.gs) or a place in `LH_PAGE_MEMORY_KEYS`, or `tests/leaderhub/no-browser-storage.test.js` fails. Edit `leader-hub/src/` and rebuild with `node tools/leaderhub-build/build.js`; tests cut code by declaration, never by line number. (10-22, 10-27)
- **leader-hub's ID token for CAS:** the browser route needs a Cloud OAuth client, which is blocked on this account. `checkCasServerSignIn()` tests the server route. Never log an ID token; log its `aud` and email. (10-23)

## Data boundaries

- **Student data never reaches Claude, the KOS Ledger or a notebook** (`cas-ccps/docs/FERPA_DATA_MAP.md`). A sheet may be read for status and timestamp columns only, and student docs, exports and the Central Ledger are never opened. A pasted row, screenshot or sheet that carries student writing is acknowledged without repeating it. Teacher-authored lesson docs and the Teacher Matrix config are fine. (10-05, 10-07, 10-17, 10-18, 10-20)
- **Ask for a count or a status column**, with a formula that returns only that (`QUERY`/`FILTER` returning counts, or an error's text before its first colon). A `FILTER` with no matches returns an error, and an `IFERROR` turns that into one misleading row. Diagnose flow output the same way: lengths, line breaks and `REGEXMATCH` flags, without reading the text. (10-21, 10-22)
- **Logs name no student.** Log row numbers and counts, never a student's address, name, text or ConfigID (the Teacher Dashboard says "a student account", `_tdWhoForLog_`). `RolloutLog` and `SubmitFailures` hold counts, codes and timestamps only. Logs the operator pastes may show ConfigIDs (`VDOE-…`), which stay out of the repo. (10-17, 10-18, 10-22, 10-29)
- **Never print a phone number or a student identifier** while checking for one: count, hash or mask it. (10-31)
- **The student-data scan** (`tools/student-data-scan/`) prints file, line, kind and hash, never the match, and reads Office and zip files too. An agent never runs `--roster`, which is the operator's, locally. An allowlist entry needs a person to look at the line, or a hash equal to a known synthetic string. A made-up address at the student domain fails CI, so use another domain when the address is only a key. Never commit a generated file or catalog that embeds Drive or roster data. (10-19, 10-21, 10-31)
- **`ReflectionLog` holds the student's own words**: a record kept with the Ledger and portfolio material, never an evaluative record. (10-24)
