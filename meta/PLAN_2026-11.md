## Packaging CAS for more teachers

### Where it stands (surveyed from the code, 2026-10-29)

Partly built for more than one teacher already:

- Ledger rows carry `TEACHER_EMAIL`, and the Teacher Dashboard shows a
  teacher only their own rows (`07`; `cas-ccps/docs/FERPA_DATA_MAP.md`: "a
  teacher only ever sees their own students' rows").
- The Student Dashboard already finds a student's rows across teachers
  and names each row's teacher (`13`).
- Parent reports are written per teacher and sent by that teacher (D1).

Single-teacher today:

- **One teacher per install.** `TEACHER_EMAIL` is one Script Property
  (`00`); the dashboard opens only for that address; the installer deploys
  one dashboard (`21`); the Ledger's nightly jobs (warm-ups 24/25,
  profiles 23, artifact sync 33, the overnight email 34c) read the one
  teacher. A second teacher on the same Ledger would get no warm-ups.
- **One school, two courses.** 8175/8177 appear in 28 script files
  (course-from-name rules in 00 and 51, the pacing guide 31, section names
  in 52); `ccpsnet.net` is a default in 00, 15b, 29 and 60, and the
  seven-digit student ID pattern is in 07, 29, 36 and 52 (re-checked
  2026-11-01); the bell schedule and early-release dates are in 00.
- **Settings are per course, not per teacher.** `LessonSchedule`,
  `CanvasSectionMap`, `PeriodOverride` and the ⚙ Settings switches have no
  teacher column: one teacher's toggle would change it for every teacher of
  that course.
- **Setup is the operator.** No current setup guide (the admin walkthrough
  is retired); about 9 Apps Script projects, 30–50 manual steps, the Studio
  Flows built by hand from `FlowBuildSpec`, the Unified Manual pinned to the
  operator's Ledger library ID.
- **The shared Ledger is a FERPA question.** Each teacher's dashboard runs
  as that teacher, so each teacher would need Drive access to one sheet
  holding every teacher's students; separation is enforced only in code.

### Two shapes (D9)

| | **A. One install per teacher** (recommended) | **B. Teachers share one install** |
|---|---|---|
| What | Each teacher gets their own Central Ledger, dashboards and Studio Flows, from the same code, set up by `run.js` from a registry per install | One Ledger and one set of flows; each teacher has their own dashboard deployment |
| FERPA | Drive-level separation: a teacher can open only their own Ledger. Matches "visible only to the student and their teachers" without relying on code alone | Every teacher needs access to every teacher's students; separation is code only |
| Code change | Configuration, not structure: courses, domain, calendar and library ID from config | Every nightly job loops over teachers; settings, schedule and section maps gain a teacher column; per-teacher ⚙ Settings |
| Operator cost | More projects to push (`run.js` already pushes many); Studio Flows built per install | One set to push; but one teacher's bad night is everyone's |
| Student who has two teachers | Two dashboards links, or the Student Dashboard reads more than one Ledger (later) | One dashboard, as today |

**Decided 2026-11-01: A, with shared context.** A is mostly
configuration, keeps the data boundary in Drive where it can be checked, and
isolates one teacher's failures. The operator asked that a student's teachers
still share what each knows about the student, so A gains one step (3b
below): teachers who share a student see each other's Student Context Doc
for that student, and no one else's.

**Shared context under A.** Today each install writes a weekly Student
Context Doc per student (29), shares it with the student to view, and keeps
its ID in the Ledger's `StudentDocRegistry`. Under A:
- A **Student Directory** sheet, shared with teachers only, holds pointers:
  student ID, teacher email, that install's context-doc ID. No grades, no
  student text. Each install upserts its own rows nightly and reads the
  rows for its own students.
- Each install shares its context doc, view only, with the student's other
  teachers from the directory. Drive enforces it: a teacher opens another
  teacher's doc only for a student they also teach.
- Each teacher's dashboard links the other teachers' docs for the student.
  Feeding them into Flow inputs or warm-ups is a later choice.
- What it exposes: which teachers teach which students (legitimate
  educational interest), far less than B's every-teacher-sees-every-student.

## Working agreements

- **No silent dead ends** (added 2026-10-29, from the audit). Work that
  stops is marked where it lives: built and off, parked (with what would
  restart it), or dropped. A handoff never drops a queue item without
  saying where it went. The dead-ends audit is repeated at each sprint
  boundary.
- One PR per change, CI green, merged on the operator's "merge".
- The 14-day window above is kept current: each handoff moves it forward
  and records the decisions made.
- The operator runs everything live and pastes logs; agents don't assume a
  run happened.
- Each phase ends with a check that says pass or fail, never a green
  "Run Completed".
- FERPA: student data stays in Google (cas-ccps, leader-hub). Claude never
  receives rosters, grades, student names or student mail. Measurements
  are counts only.

## Standing risks

- **Bus factor of one.** Packaging is also the mitigation: the setup guide
  and a second install that someone else stood up are the first proof that
  CAS runs without its builder.
- **Parts multiply runs.** About 2.5× the returns means 2.5× the chances a
  run fails, and an unlock waits on Flow 2. D8 waits on the numbers for
  this reason.
- **Studio is hand-built.** Each install's flows are built by hand in
  Studio; a second install doubles that work and its drift. The setup
  guide and `checkFlowBinding()` are the control.
