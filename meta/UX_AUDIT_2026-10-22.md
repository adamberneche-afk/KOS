# UX audit of the KOS monorepo, by stakeholder (2026-10-22)

**What this is.** An end-to-end review of every surface a person sees in
the three systems (cas-ccps, leader-hub, kos-personal), taken one
stakeholder at a time: students, the classroom teacher, families, the
operator and future adopting teachers, the leader-hub owner and the people
it reaches, and the kos-personal operator. Read from `main` at `ffb5172`.

**How it was checked.** Six parallel read-only reviews. Each one read the
code paths and rendered the real pages through the GAS sandbox
(`tests/harness/gas-sandbox.js`) with `google.script.run` stubbed, then took
screenshots in headless Chromium at phone (390px), tablet (820px) and laptop
(1366px) widths and drove keyboard tests. The most severe claims were
spot-checked against the code before filing. Nothing was changed by the
audit. Findings 1-21 of
[`DASHBOARD_WALKTHROUGH_2026-10-26.md`](./DASHBOARD_WALKTHROUGH_2026-10-26.md)
are not repeated here.

**Severity.** *blocks-task*: someone can't do the thing, or loses work.
*misleading*: the screen says something false. *safety* / *privacy*: data
or students at risk. *friction*, *polish*: true but costly or rough. Line
numbers are on `ffb5172`. No student names, emails or IDs appear here.

## What the reviews have in common

1. **The same fact, written differently on every surface.** One state has six names across the doc header, the card, the feedback comment, the doc menu, the Quick Start and Canvas ("Meets the standard" / "Passed ✓" / "RESULT: YOUR WORK MEETS THE STANDARD"). There are two "+ New Lesson" buttons that do different things, two "current" lessons from different sources, and two opposite /5 scales. leader-hub has two season labels, and kos-personal has four names for "setup not done". The fix is structural: one wording table per system (in 00 for cas-ccps), used by every surface, with generated docs.
2. **Failures land on the person least able to fix them.** Students see "Flagged"; teachers get raw-sheet instructions; the operator gets silence (finding 5) or names without fixes in the overnight email. Each failure needs an owner, honest wording ("taking longer than usual — your teacher knows"), and one action where its owner works (a "Retry evaluation" on the teacher's row).
3. **The docs describe older systems.** These pages all describe a version that no longer exists:
   - cas-ccps: Student Quick Start, the Teacher Reference Guide and Quick Start, the admin walkthrough, the Studio flow reference, and the Unified Manual's setup tab.
   - kos-personal: the deployment guide's banner.
   - leader-hub: the season templates.

   These pages are where a new person starts. Retire or rewrite them, rather than adding more banners.
4. **The UI drops what the server already knows.** Examples:
   - kos-personal: the server returns `docUrl`, the council ID and data-quality flags, and the UI discards them.
   - cas-ccps: `ParentReportLog` already holds the last recipient, and the SCR queue already knows which items are confirmable, but the dashboards don't use either.

   Many fixes here are display changes, not new features.
5. **The operator is the system's runtime.** About 139 runnable functions sit in the Central Ledger dropdown, and only 13 are in a menu. The order to run them lives in the handoff docs. Script Properties serve as function arguments. Each push ends in hand checks across up to 9 editor tabs. The 10-22 queue has about 40 manual actions. Adoption is blocked on deployment and setup, not on courses: the course builder plan should gain an onboarding phase first.

**Before D1 turns reports on, these must be true:**
1. Scores and ratings appear in words, with the scale's direction stated.
2. Each item shows its real status.
3. Every rostered student gets a report, including "nothing turned in".
4. "Progress" is limited to the current term.
5. Competency text replaces the IDs.
6. Recipients come from a verified guardian list that allows several guardians and blocks 18+ students, restricted contacts and opt-outs.
7. Each report has a signature, contact details and a "what to do" line.

The dry run should review one report for each case (nothing turned in,
revision, mixed, no name, first week, translation), ideally read back by a
real parent.
